# Spec Delta

## Purpose

Предоставляет пользователю веб-интерфейс запуска и просмотра расчётов потребностей производства на странице плана через существующий REST-контракт `/api/v1/plans/{planId}/calculations`.

## ADDED Requirements

### Requirement: Типы расчёта потребностей
Frontend SHALL описывать ответ backend типами `RequirementCalculationView` (поля `id` и `planId` вида `{value}`, `executedAt` как ISO-строка, `items`) и `RequirementItemView` (поле `type` со значениями `PART`/`ASSEMBLY`/`BUY`/`STANDART`/`VZK`, поля `id`, `number`, `name`, `quantity`, `needType` со значениями `MANUFACTURE`/`PURCHASE`, `unit` и `sources` как массив объектов вида `{value}`).

#### Scenario: Соответствие контракту backend
- **WHEN** фронтенд получает расчёт потребностей от backend
- **THEN** поля расчёта и каждой позиции соответствуют перечисленным типам без дополнительных или отсутствующих полей

### Requirement: Клиентские методы расчётов
Frontend SHALL предоставлять в `planningApi` методы `calculate(planId)` для запуска расчёта через `POST /api/v1/plans/{planId}/calculations`, `listCalculations(planId)` для истории через `GET /api/v1/plans/{planId}/calculations` и `getCalculation(planId, calculationId)` для чтения одного расчёта через `GET /api/v1/plans/{planId}/calculations/{calculationId}`.

#### Scenario: Пути запросов
- **WHEN** фронтенд запускает расчёт, читает историю или читает один расчёт
- **THEN** запросы отправляются на указанные пути с методом POST/GET соответственно

### Requirement: Человекочитаемые ошибки расчёта
Функция `humanizeRequirementError` SHALL возвращать русские сообщения: «Запись не найдена» для `not_found`, «В спецификации обнаружен цикл» для `bom_cycle`, сообщение о переполнении количества для `quantity_overflow` и сообщение об отсутствующей сборке с идентификатором проблемной ссылки для `specification_item_not_found`.

#### Scenario: Код not_found
- **WHEN** ошибка расчёта имеет код `not_found`
- **THEN** функция возвращает «Запись не найдена»

#### Scenario: Код bom_cycle
- **WHEN** ошибка расчёта имеет код `bom_cycle`
- **THEN** функция возвращает «В спецификации обнаружен цикл»

#### Scenario: Код quantity_overflow
- **WHEN** ошибка расчёта имеет код `quantity_overflow`
- **THEN** функция возвращает сообщение о переполнении количества

#### Scenario: Код specification_item_not_found
- **WHEN** ошибка расчёта имеет код `specification_item_not_found` и идентификатор проблемной ссылки
- **THEN** функция возвращает сообщение об отсутствующей сборке с этим идентификатором

### Requirement: Секция расчётов на странице плана
Страница `PlanDetail` SHALL отображать секцию «Расчёты потребностей» с кнопкой запуска только после успешной загрузки плана, и SHALL не отображать эту секцию во время загрузки или при ошибке загрузки плана.

#### Scenario: План загружен
- **WHEN** план успешно загружен на странице плана
- **THEN** отображается секция «Расчёты потребностей» с кнопкой запуска расчёта

#### Scenario: План не загружен
- **WHEN** план находится в состоянии загрузки или ошибки
- **THEN** секция «Расчёты потребностей» не отображается

### Requirement: Запуск расчёта
При нажатии кнопки запуска Frontend SHALL отправлять `POST /api/v1/plans/{planId}/calculations`, и при ответе 201 SHALL показывать полученный расчёт и обновлять историю без перезагрузки страницы.

#### Scenario: Успешный запуск
- **WHEN** пользователь нажимает кнопку запуска и backend возвращает 201 с расчётом
- **THEN** интерфейс показывает позиции полученного расчёта и добавляет его в историю

### Requirement: Пустой план
Для плана без элементов кнопка запуска SHALL оставаться активной, и после ответа 201 интерфейс SHALL показывать «Позиции отсутствуют» и не рендерить пустую таблицу позиций.

#### Scenario: Расчёт пустого плана
- **WHEN** пользователь запускает расчёт плана без элементов и backend возвращает 201 с пустым списком позиций
- **THEN** интерфейс показывает «Позиции отсутствуют» и не отображает таблицу позиций

### Requirement: История расчётов
Секция SHALL загружать историю расчётов при открытии страницы плана, отображать записи в порядке из API (новые первыми) и показывать `executedAt` в человекочитаемом виде.

#### Scenario: Загрузка истории
- **WHEN** открывается страница загруженного плана
- **THEN** запрашивается список расчётов и записи отображаются в порядке, возвращённом API, с человекочитаемым временем выполнения

### Requirement: Просмотр расчёта
Выбор расчёта из истории SHALL раскрывать таблицу его позиций, где каждая строка показывает тип, номер, наименование, количество, вид потребности, единицу и источники.

#### Scenario: Раскрытие расчёта
- **WHEN** пользователь выбирает расчёт из истории
- **THEN** отображается таблица со всеми перечисленными колонками для каждой позиции

### Requirement: Подписи вида потребности
Frontend SHALL отображать вид потребности русскими подписями: `MANUFACTURE` — «изготовить», `PURCHASE` — «закупить».

#### Scenario: Подписи потребности
- **WHEN** позиция имеет `needType` `MANUFACTURE` или `PURCHASE`
- **THEN** в таблице отображается «изготовить» или «закупить» соответственно

### Requirement: Подписи типа позиции
Frontend SHALL отображать тип позиции русскими подписями: `PART` — «Деталь», `ASSEMBLY` — «Сборка», `BUY` — «Покупной», `STANDART` — «Стандартный», `VZK` — «ВЗК».

#### Scenario: Подписи типа
- **WHEN** позиция имеет один из пяти типов каталога
- **THEN** в таблице отображается соответствующая русская подпись

### Requirement: Разрешение источников
Frontend SHALL отображать источники позиции как номер и название головной сборки плана по UUID источника, и SHALL показывать «Сборка не найдена» для UUID, который не удалось разрешить, без ошибки рендера.

#### Scenario: Разрешённый источник
- **WHEN** UUID источника совпадает со сборкой плана
- **THEN** в колонке источников отображаются номер и название этой сборки

#### Scenario: Неразрешимый источник
- **WHEN** UUID источника не соответствует ни одной известной сборке
- **THEN** отображается плейсхолдер «Сборка не найдена»

### Requirement: Порядок позиций
Frontend SHALL отображать позиции расчёта в порядке, возвращённом API, и SHALL не пересортировывать их на клиенте.

#### Scenario: Сохранение порядка
- **WHEN** расчёт содержит позиции в определённом порядке
- **THEN** таблица отображает их в том же порядке без клиентской сортировки

### Requirement: Ошибки запуска расчёта
При ошибке запуска Frontend SHALL показывать баннер с соответствующим сообщением, не показывать частичный или ложный результат и не изменять историю расчётов.

#### Scenario: Цикл BOM
- **WHEN** запуск возвращает 409 с кодом `bom_cycle`
- **THEN** показывается баннер «В спецификации обнаружен цикл», таблица не отображается, история не меняется

#### Scenario: Переполнение количества
- **WHEN** запуск возвращает 400 с кодом `quantity_overflow`
- **THEN** показывается баннер о переполнении количества, таблица не отображается, история не меняется

#### Scenario: Отсутствующий план
- **WHEN** запуск возвращает 404 с кодом `not_found`
- **THEN** показывается баннер «Запись не найдена», таблица не отображается, история не меняется

#### Scenario: Отсутствующая сборка в спецификации
- **WHEN** запуск возвращает 404 с кодом `specification_item_not_found`
- **THEN** показывается баннер об отсутствующей сборке с идентификатором ссылки, таблица не отображается, история не меняется

### Requirement: Ошибки чтения истории
При ошибке чтения истории или расчёта Frontend SHALL показывать в секции сообщение «Запись не найдена» для кода `not_found`.

#### Scenario: Ошибка чтения
- **WHEN** запрос истории или расчёта возвращает 404 с кодом `not_found`
- **THEN** в секции отображается «Запись не найдена»

### Requirement: Блокировка запуска
Во время выполнения запроса запуска Frontend SHALL блокировать кнопку запуска и показывать состояние «Расчёт…», а также SHALL исключать повторную отправку запроса.

#### Scenario: Запрос в процессе
- **WHEN** запрос запуска расчёта находится в процессе выполнения
- **THEN** кнопка запуска заблокирована, отображается «Расчёт…», повторный запуск невозможен

### Requirement: Неизменность существующего UI
Существующий UI «Плоская структура» и существующие страницы планов SHALL сохранять прежнее поведение и структуру: таблица плоской структуры продолжает показывать колонки «Номер», «Название» и «Количество».

#### Scenario: Плоская структура без изменений
- **WHEN** пользователь открывает плоскую структуру плана
- **THEN** она работает как раньше и отображает колонки «Номер», «Название» и «Количество»
