# Design

## Context

Текущий frontend построен вокруг одного `App`: он загружает список выбранного типа, показывает `CatalogTable`, а `SpecificationPanel` самостоятельно принимает идентификатор сборки. `catalogApi` уже содержит list/create/rename/remove, а `specificationApi` — все операции строк и копирования; backend-контракты менять не требуется.

## Goals / Non-Goals

**Goals:**

- Организовать два state-based представления: список и деталь, с возвратом без изменения URL.
- Передавать выбранную запись и идентификатор сборки между представлениями без ручного ввода.
- Сохранить единые API-клиенты, существующие сообщения ошибок и состояния загрузки.
- Обеспечить тестируемое поведение всех пяти типов каталога и спецификации.

**Non-Goals:**

- React Router, URL-маршруты, deep links и браузерная навигация.
- Изменение backend API, доменной модели или схемы базы данных.
- Изменение бизнес-правил спецификации и добавление новых операций.

## Decisions

### D1. State-based навигация в `App`

Состояние приложения будет хранить выбранный тип, текущий экран (`list`, `catalog-detail`, `specification-detail`) и выбранную запись. Переходы будут выполняться обработчиками событий, а «Назад» возвращать на предыдущее представление. React Router не добавляется: URL-роутинг явно отложен.

**Альтернатива:** React Router — отклонена, поскольку URL-роутинг не входит в согласованный scope.

### D2. Отдельные представления деталей каталога и спецификации

Детальная страница каталога будет получать запись по `GET /api/v1/{type}/{id}` и будет единым компонентом для пяти типов. Для Assembly она дополнительно покажет действие «Состав», которое открывает спецификацию с уже известным `assemblyId`. Логику строк и копирования следует переиспользовать из текущего `SpecificationPanel`, убрав форму ручного открытия сборки.

**Альтернатива:** сохранить отдельную глобальную панель спецификации — отклонена, поскольку она допускает ввод несвязанного UUID и нарушает навигационную модель.

### D3. Запись только с детальной страницы

`CatalogTable` будет отвечать только за отображение и выбор строки. Кнопки переименования и удаления переносятся в detail view; удаление сохраняет `window.confirm`. После успешных операций detail view обновляет данные или возвращает список согласно требованиям.

### D4. API для одной записи

В `catalogApi` добавляется типизированная операция получения одной записи, использующая существующий endpoint `/api/v1/{type}/{id}`. List/create/rename/remove и `specificationApi` остаются общими для всех типов и используют существующую обработку `ApiClientError`.

### D5. Состояния и конкурентные действия

Для загрузки списка, детали и строк спецификации используются явные состояния `loading/ready/error`. Формы операций блокируются на время активного запроса; после успешных rename/delete и операций спецификации состояние перечитывается через соответствующий GET, чтобы UI отражал серверное состояние.

### D6. Тестирование

Vitest + Testing Library расширяются тестами `App` и детальных представлений: переход по строке, отображение полей, возврат, GET одной записи, rename/delete на детали, переход к составу и операции строк/копирования. API-тесты проверяют новый метод получения одной записи и сохранение существующих endpoint-контрактов.

## Risks / Trade-offs

- **[Риск]** При state-based навигации обновление страницы теряет текущую деталь. → **Митigation:** это принятое ограничение до введения URL-роутинга; поведение покрыть тестом переходов внутри текущего сеанса.
- **[Риск]** Повторная загрузка после каждой операции может давать кратковременное состояние загрузки. → **Митigation:** явно показывать индикатор и блокировать соответствующую активную операцию.
- **[Риск]** Backend может вернуть запись, удалённую между списком и открытием детали. → **Митigation:** показывать человекочитаемую ошибку 404 и предоставлять «Назад».
- **[Компромисс]** Общее представление деталей уменьшает дублирование, но требует передавать конфигурацию типа и условно показывать «Состав» только для Assembly.

## Migration Plan

Изменение разворачивается как frontend-сборка без миграции базы данных и без изменения backend. Откат выполняется возвратом предыдущей frontend-сборки; backend endpoints остаются совместимыми.

## Open Questions

Нет: согласованные решения определяют навигацию, размещение операций и границы спецификации.
