# Design

## Context

Существующая спецификация хранит только прямые `SpecificationRow`, а `SpecificationApplicationService` уже имеет доступ к tenant-контексту, репозиторию спецификаций и `AssemblyService`. Данные каталога для отображения номера и имени доступны через публичные tenant-scoped сервисы `catalog.api`; REST-контроллер и `RestExceptionHandler` уже задают контракт и формат ошибок.

## Goals / Non-Goals

**Goals:**

- Выполнять обход BOM на backend без изменения сохранённых прямых строк.
- Сохранять границы модулей: спецификации используют только публичный API каталога.
- Возвращать стабильный DTO плоского элемента и детерминированную сортировку.
- Гарантировать завершение с диагностируемой ошибкой при цикле.

**Non-Goals:**

- Новый persisted-ресурс или кэш плоских результатов.
- Изменение правил добавления прямых строк.
- Поддержка дробных количеств, альтернатив или производственного расчёта.

## Decisions

### D1. Вычислять результат при запросе
Плоский состав вычисляется заново для каждого вызова endpoint и не сохраняется. Это исключает рассинхронизацию с изменёнными прямыми строками; альтернативой было бы хранение производного результата, что потребовало бы механизмов инвалидирования.

### D2. Разделить обход и обогащение листьев
Обход использует `SpecificationRepository` для получения прямых строк сборок и набор сборок текущей цепочки для обнаружения циклов. После накопления идентификаторов листьев application-слой получает `number` и `name` через соответствующие публичные сервисы каталога и формирует DTO. Доменная модель не получает зависимостей от Spring, JPA или каталоговых адаптеров.

### D3. Использовать типизированные счётчики листьев
Накопление выполняется по полному `CatalogItemReference` (тип + UUID), поэтому одинаковые UUID разных типов не смешиваются. Количество передаётся по цепочке как целое значение; реализация должна явно обработать переполнение выбранного числового типа отказом, а не возвращать неверное количество.

### D4. Отслеживать текущий путь, а не глобальное посещение
Сборка считается циклической только если встречена в текущем стеке обхода. Одинаковая дочерняя сборка, подключённая из двух независимых ветвей, обходится по обеим ветвям и корректно даёт сумму вкладов. Альтернатива — глобальный visited-набор — могла бы ошибочно пропустить второй вклад.

### D5. Выделить отдельный контракт flat endpoint
Используется `GET /api/v1/specifications/{assemblyId}/flat`, не изменяющий существующий `/rows`. Ответ содержит плоский массив `{number, name, quantity}`; код `bom_cycle` маппится на HTTP 409 через существующий механизм REST-ошибок.

### D6. Управлять состоянием плоского результата отдельно от прямых строк
Frontend хранит результат, статус и ошибку плоского запроса независимо от загрузки прямых строк. Это позволяет повторить операцию после ошибки и не заменяет уже показанные прямые строки частичным или устаревшим результатом.

## Risks / Trade-offs

- **[Переполнение количества при глубокой/широкой структуре] →** использовать тип, достаточный для промежуточного расчёта, и явно отклонять результат при невозможности представить количество в API-контракте.
- **[Много вызовов каталоговых сервисов] →** обогащать каждый уникальный лист один раз за запрос; не добавлять кэш между запросами до появления измеренной потребности.
- **[Цикл может существовать в данных из-за разрешённых косвенных ссылок] →** проверять текущий путь до рекурсивного обхода дочерней спецификации и возвращать исключение до формирования ответа.
- **[Неполная спецификация или отсутствующий лист] →** использовать существующую семантику каталоговых сервисов: ошибка отсутствующего элемента должна быть преобразована общим REST-обработчиком, без возврата фиктивных полей.

## Migration Plan

Изменение не требует миграции данных или схемы БД. После выкладки новый endpoint доступен вместе с обновлённым frontend; rollback выполняется удалением/откатом приложения, существующие endpoints `/rows` остаются совместимыми.

## Open Questions

Нет: статус и код ошибки цикла, состав листовых типов, алгоритм количеств и endpoint согласованы в рамках задачи.
