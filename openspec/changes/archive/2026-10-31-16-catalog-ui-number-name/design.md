# Design

## Context

Существующий frontend загружает список только активного типа каталога, а строки спецификации содержат `{type,id}`. Таблица спецификации показывает тип и UUID, а форма добавления принимает UUID вручную. Каталог уже предоставляет поля `number` и `name`; backend-контракты изменения не требуют.

## Goals / Non-Goals

**Goals:**

- Использовать `number` и `name` как единственные идентифицирующие значения, видимые пользователю.
- Обеспечить локальную фильтрацию загруженных записей каталога и выбор элемента из списка выбранного типа.
- Сохранить id во внутреннем состоянии ровно настолько, чтобы выполнять существующие операции спецификации.
- Сохранить текущие состояния загрузки и обработки ошибок.

**Non-Goals:**

- Изменение REST API, backend или формата `CatalogItemReference`.
- Серверная фильтрация, пагинация или новый механизм загрузки каталога.
- Изменение бизнес-правил спецификаций.

## Decisions

### D1. Фильтрация выполняется на клиенте

Фильтр списка каталога и поиск в выпадающем списке применяются к уже загруженным данным. Сравнение выполняется без учёта регистра по подстроке отдельно в `number` и `name`; запросы каталога не меняются.

**Альтернатива:** добавление query-параметров к API отклонено, поскольку backend не изменяется и список уже загружается целиком.

### D2. Источник резолва строк — загруженные списки каталога

Для пяти типов каталога frontend поддерживает доступ к загруженным `CatalogEntry` и сопоставляет ссылку спецификации по типу и id. Отображение строки использует найденные `number` и `name`, а id остаётся внутренним значением для PUT/DELETE/POST.

**Альтернатива:** отдельный GET для каждой строки отклонён, чтобы не создавать дополнительные запросы и не менять UX загрузки.

### D3. Выбор элемента моделируется как тип + поисковый список

Форма сохраняет отдельный выбор типа `PART`, `ASSEMBLY`, `BUY`, `STANDART` или `VZK`. После смены типа набор кандидатов и выбранный элемент сбрасываются/пересчитываются; выбор отображается номером и названием. Отправка строит прежнее тело запроса с id выбранной записи.

**Альтернатива:** свободный ввод номера/названия отклонён, поскольку он не гарантирует однозначного соответствия записи и id.

### D4. Не найденный резолв не раскрывает UUID

Если ссылка строки не сопоставляется с загруженным каталогом, интерфейс показывает безопасное состояние отсутствующих данных (например, «Элемент не найден») и не выводит UUID. Действия строки продолжают использовать исходную ссылку.

## Risks / Trade-offs

- **[Риск]** Список каталога может быть устаревшим или неполным → обновлять/загружать данные каталогов в рамках состояния экрана спецификации и покрыть сценарии отсутствующего элемента тестами.
- **[Риск]** Большой список увеличит объём client-side фильтрации → использовать простое линейное сравнение загруженных записей без добавления преждевременной инфраструктуры.
- **[Риск]** Изменение доступных текстовых меток сломает существующие UI-тесты → обновить тесты на пользовательские сценарии, сохранив проверки REST-тел запросов.

## Open Questions

Нет. Согласованные решения определяют поведение и границы изменения.
