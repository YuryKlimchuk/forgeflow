# Proposal

## Why

Интерфейс спецификации сейчас требует ручного ввода UUID и показывает пользователю внутренний идентификатор, тогда как рабочие данные каталога представлены номером и названием. Это усложняет выбор элемента и затрудняет чтение спецификации; изменение устраняет UUID из пользовательского сценария без изменения backend-контрактов.

## What Changes

- Добавить client-side поиск записей каталога по `number` или `name` без учёта регистра и по подстроке на экране списка.
- Заменить отображение `Тип`/`ID` в таблице строк спецификации на `Номер`/`Название`/`Количество`.
- Резолвить номер и название строк спецификации по загруженным спискам каталога, сохраняя внутренний id только для API-запросов.
- Заменить ручное поле `ID элемента` в форме добавления строки на выпадающий список элементов выбранного типа с поиском по номеру и названию.
- Сохранить выбор типа элемента, передачу его id в существующий POST и текущие операции изменения количества, удаления, копирования и плоской структуры.
- Не изменять backend, REST-контракты или форматы запросов и ответов.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `frontend-catalog`: изменяется поведение поиска каталога, отображения строк спецификации и выбора элемента при добавлении строки.

## Impact

Затрагиваются React-компоненты и тесты frontend в `frontend/src/`, прежде всего `App.tsx`, `CatalogTable.tsx`, `SpecificationDetail.tsx` и связанные типы/состояния в `api.ts`. Backend, REST endpoints, доменная модель и форматы API не изменяются; новые зависимости не требуются.

## Non-goals

- Изменение backend или API-контрактов.
- Изменение идентификаторов, хранимых и передаваемых внутри приложения.
- Изменение операций копирования спецификации, изменения количества, удаления строк или получения плоской структуры.
- Серверный поиск, пагинация или изменение загрузки каталогов.
