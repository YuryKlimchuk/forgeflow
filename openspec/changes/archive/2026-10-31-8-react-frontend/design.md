# Design

## Context

См. `proposal.md` для мотивации изменения. Фронтенд создаётся как независимая папка `frontend/` рядом с Java-бэкендом и использует уже существующие маршруты `/api/v1/parts`. Он не добавляет Spring Modulith-модуль и не изменяет серверный контракт.

## Goals / Non-Goals

**Goals:**

- Дать React-приложению минимальный экран управления деталями каталога.
- Изолировать HTTP-вызовы и преобразование REST-ошибок от компонентов интерфейса.
- Обеспечить воспроизводимую локальную разработку через Vite proxy и проверяемый минимум UI-тестов.

**Non-Goals:**

- Изменение Java-кода, REST API, аутентификации или tenant-логики.
- Клиентская маршрутизация, глобальное состояние, UI-кит, Tailwind и интеграционные тесты с реальным бэкендом.
- Реализация других разделов ForgeFlow, пагинации, поиска или расширенного управления каталогом.

## Decisions

### D1. Vite + React + TypeScript

Фронтенд будет scaffold-иться как самостоятельное Vite-приложение с React и TypeScript. Vite выбран вместо отдельной webpack-конфигурации из-за компактной dev/build-конфигурации и встроенного proxy; TypeScript фиксирует DTO и состояния UI на границе API.

### D2. npm и независимая папка

`frontend/` получает собственные `package.json`, lock-файл и команды разработки/тестирования. npm используется напрямую; workspaces, Turborepo и иные оркестраторы не вводятся, чтобы не связывать жизненные циклы Maven-бэкенда и фронтенда.

### D3. Нативный fetch и Vite proxy

API-клиент использует нативный `fetch()` и базовый путь `/api/v1/parts`. В dev-конфигурации Vite запросы `/api` проксируются на `http://localhost:8080`, поэтому браузеру не требуется CORS-настройка. Axios не добавляется.

### D4. Локальное состояние React

Загрузка списка, форма, текущая операция и ошибка управляются React hooks в пределах экранов/компонентов. Роутер и внешний state manager не добавляются: первый срез содержит один экран и небольшой объём состояния.

### D5. Разделение API и UI-компонентов

Типы DTO и API-функции выделяются в клиентский слой. Экран каталога состоит из таблицы, формы создания и управляющих элементов переименования/удаления; подтверждение удаления реализуется браузерным confirm либо эквивалентным контролом без отдельной библиотеки модалок. Ошибка ответа нормализуется в человекочитаемое сообщение с отдельными случаями `duplicate`, `bad_request` и `not_found`.

### D6. CSS с CSS-переменными и заданной палитрой

Стили пишутся обычным CSS. CSS-переменные задают светлую тему, графитовый акцент RAL 7024 (приблизительно `#474A51`), светлую подложку RAL 7032 (приблизительно `#B8B4A6`), тонкие границы и читаемые состояния таблицы. UI-кит и Tailwind не используются.

### D7. Vitest и React Testing Library

Vitest запускается в jsdom-окружении с React Testing Library. Тесты проверяют рендер списка, отправку формы создания и отображение нормализованной ошибки; `fetch` мокируется, а реальный REST-бэкенд в тестовый контур не включается.

## Risks / Trade-offs

- [Риск] Контракт API или формат дат изменится → типы DTO и маппинг проверяются по текущему `PartView`, а формат даты отображается через отдельную функцию, которую можно изменить без переписывания компонентов.
- [Риск] Браузерная авторизация/сессия не настроена в dev-среде → запросы остаются same-origin через proxy; проверка связки выполняется с запущенным бэкендом и его демо-пользователем.
- [Риск] `confirm` ограничивает визуальный контроль диалога → для первого среза это исключает зависимость от UI-кита; при необходимости отдельный компонент модалки можно добавить позднее без изменения REST-контракта.
- [Риск] Независимый frontend не входит в Maven lifecycle → команды `npm ci`, `npm run test` и `npm run build` явно документируются в задачах и проверяются отдельно.

## Migration Plan

Миграция данных и серверных контрактов не требуется. Развёртывание включает публикацию собранного содержимого `frontend/` выбранным статическим способом; откат выполняется удалением/возвратом фронтенд-артефакта, Java-бэкенд при этом не меняется.
