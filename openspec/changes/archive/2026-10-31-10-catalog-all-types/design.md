# Design

## Context

Существующий вертикальный срез `Part` задаёт рабочий контракт для каталога: tenant-scoped application service, in-memory repository, REST-контроллер и React-формы/таблица. `Assembly` имеет частичный адаптер, а `Buy`, `Standart` и `Vzk` — только доменные порты. Требования дельты в `specs/` фиксируют расширение поведения без изменения существующих маршрутов Part.

## Goals / Non-Goals

**Goals:**

- Дать четырём типам тот же полный вертикальный срез и те же CRUD-семантики, что у Part.
- Сохранить границы Spring Modulith, hexagonal dependency direction и tenant-изоляцию.
- Сделать frontend единым экраном с типобезопасным generic-клиентом.
- Сохранить seed-поведение: начальные данные только для Part и Assembly.

**Non-Goals:**

- Добавление PostgreSQL-адаптеров, миграций, BOM-связей или новых бизнес-правил.
- Изменение URL, DTO или поведения существующего Part API.
- Унификация доменных агрегатов в общий backend generic/base-класс.

## Decisions

### D1. Явная репликация backend-паттерна Part

Для каждого типа создаются отдельные API DTO, service port, application service, mapper, exceptions, repository adapter и controller. Это выбрано вместо backend generic-абстракции: типизированные доменные агрегаты остаются явными, а Spring Modulith boundaries и диагностируемые контракты не скрываются общей иерархией.

### D2. Rich model для переименования

`rename` добавляется в каждую из четырёх доменных сущностей и отвечает за валидацию non-blank, изменение имени и `updatedAt`. Application service не будет дублировать это правило; он только разрешает агрегат через tenant-scoped порт и сохраняет результат.

### D3. Repository contract без delete

Все пять repository-портов получают одинаковые операции `save`, `findById`, `findAll`, `existsByNumber`. Soft-delete выполняется доменным `markDeleted()` с последующим `save`; in-memory адаптеры фильтруют удалённые записи, tenant и сортировку по `number` в read-операциях.

### D4. Единая REST URL-схема

Для дополнительных типов используются множественные noun-пути `/api/v1/assemblies`, `/api/v1/buys`, `/api/v1/standarts`, `/api/v1/vzks`; переименование использует существующий шаблон `/{id}/name`. Контроллеры остаются тонкими и зависят только от `catalog.api` портов.

### D5. Composition root в WebConfig

Репозитории, application services и контроллеры регистрируются явными `@Bean` в корневом `WebConfig`. Это сохраняет текущую схему wiring и не вводит component scanning или скрытые межмодульные зависимости.

### D6. Generic только на frontend

Frontend описывает конфигурацию типа (`label`, `endpoint`) и использует общий клиент list/create/rename/delete и общие компоненты. Backend generic-слой не вводится, поскольку доменные типы имеют отдельные публичные контракты.

### D7. Тестирование по матрице типов

Существующие Part-тесты сохраняются. Для четырёх типов добавляются аналогичные unit-тесты сервисов, репозиториев и mapper'ов, MVC-тесты контроллеров; React-тесты проверяют все вкладки, endpoint mapping и CRUD. Архитектурная проверка `ApplicationModules.verify()` выполняется в финальном шаге.

## Risks / Trade-offs

- [Риск] Четыре явных backend-среза увеличивают объём кода → использовать Part как структурный эталон и проверять единообразие тестовой матрицей.
- [Риск] Ошибка в endpoint-конфигурации может направить вкладку к чужому типу → покрыть каждый label отдельным frontend-тестом и проверять URL.
- [Риск] In-memory storage не моделирует долговременную персистентность → явно не расширять scope; PostgreSQL-адаптер остаётся отдельной задачей.
- [Риск] Удаление старого `delete` из Assembly-порта затронет seed/wiring → сначала найти все вызовы и перевести их на `markDeleted` + `save`, затем выполнить компиляционные и интеграционные тесты.

## Migration Plan

Изменение не требует миграции базы данных. Реализация выполняется от домена к адаптерам, затем включается frontend; rollback выполняется возвратом change до деплоя, поскольку существующий Part API и схема БД не меняются.

## Open Questions

Нет: URL, названия вкладок, seed-ограничение и поведение всех пяти типов заданы в запросе и спецификациях.
