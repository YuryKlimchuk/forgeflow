# Design

## Context

См. мотивацию в `proposal.md` и поведенческие контракты в `specs/planning`, `specs/planning-rest` и `specs/frontend-catalog`. ForgeFlow использует модульный монолит с разделением `api/application/domain/infrastructure`, tenant-контекстом `OrganizationContext`, in-memory репозиториями и сборкой зависимостей в `WebConfig`. `catalog.api.AssemblyService` валидирует доступность головы-сборки, а `specifications.api.SpecificationService.flatten` уже возвращает листы `number`/`name`/`quantity`.

## Goals / Non-Goals

**Goals:**

- Добавить самостоятельный модуль `planning` с богатым агрегатом и изоляцией по организации.
- Сохранить модульные границы и использовать только named interface `catalog`, `specifications` и `shared`.
- Дать REST и React-клиенту единый контракт, не раскрывающий UUID в UI.
- Проверить доменные правила, REST-ошибки, tenant-изоляцию и суммирование нескольких сборок тестами.

**Non-Goals:**

- Перевод in-memory хранения на PostgreSQL.
- Изменение алгоритма или контракта плоского разворачивания спецификации.
- Реализация календарного, складского или мощностного планирования.

## Decisions

### D1. Модульная граница и зависимости

Создать пакет `com.hydroyura.forgeflow.planning` с `@ApplicationModule(type = OPEN, allowedDependencies = {"catalog :: catalog", "specifications :: specifications", "shared :: shared"})`. Внутри разместить публичные DTO/сервис в `api`, сценарии в `application`, агрегат и порт репозитория в `domain`, in-memory адаптер в `infrastructure`. Это сохраняет направленные зависимости и позволяет web-слою использовать только API.

Альтернатива — разместить планирование в `specifications` — отклонена: план является отдельным бизнес-контекстом, а требуемая архитектурная зависимость явно направлена из `planning` в спецификации.

### D2. Модель агрегата

`Plan` будет корнем агрегата с идентификатором, именем, годом, месяцем и коллекцией `PlanItem(AssemblyId, quantity)`. Инварианты месяца, количества и уникальности сборки проверяются доменной моделью; уникальность имени проверяется application-сервисом через tenant-scoped порт репозитория. Изменения элементов выполняются через методы агрегата, а не через публичную мутацию коллекции.

### D3. Tenant-scoped хранение

Порт репозитория и application-сервис получают текущий `OrganizationId` из `OrganizationContext`. In-memory адаптер индексирует планы по организации и идентификатору; поиск имени и плана не выполняется глобально. Tenant не включается в DTO, URL или тело запроса.

### D4. Расчёт плоской структуры

`PlanService.flatten` сначала получает план текущей организации, затем для каждого `PlanItem` вызывает `SpecificationService.flatten(assemblyId)`, умножает количество каждого результата на количество элемента и объединяет строки по `number`. Для итогового имени используется имя листа из результата разворачивания; итог сортируется по `number`. Алгоритм не дублирует обход BOM и поэтому наследует обработку циклов и tenant-контекст существующего сервиса спецификаций.

Альтернатива — повторно обходить прямые строки спецификации в planning — отклонена, поскольку нарушает границу модулей и дублирует бизнес-правило flatten.

### D5. REST-маршруты и ошибки

Контроллер в `web` использует базовый путь `/api/v1/plans`: `POST` и `GET` для коллекции, `GET` для `/plans/{id}`, `POST` для `/plans/{id}/items`, `PUT` и `DELETE` для `/plans/{id}/items/{assemblyId}`, `GET /plans/{id}/flat`. Тонкий контроллер преобразует UUID в типизированные ID и делегирует сервису. `RestExceptionHandler` получает отдельные маппинги planning-исключений: валидация — 400 `bad_request`, отсутствие ресурса — 404 `not_found`, конфликт имени/элемента — 409 `duplicate`; ошибка цикла, пришедшая от flatten, сохраняет существующий код `bom_cycle` и статус 409.

### D6. Frontend-навигация и отображение

Добавить отдельное состояние/раздел планов в state-based навигацию `App.tsx`, API-функции `planningApi` в `api.ts`, список, форму создания и детальный компонент. Список сборок для элемента загружается из существующего каталожного индекса и фильтруется по номеру/названию; выбранный элемент показывается текстом, а не UUID. Период форматируется на UI по числовым year/month. UI повторяет существующие loading/error-паттерны и блокирует активную операцию до ответа.

### D7. Тестовая стратегия

Добавить unit-тесты агрегата и `PlanService`, включая дубликаты, границы месяца/количества, tenant-изоляцию и flatten по нескольким сборкам. Добавить controller-тесты маршрутов и кодов ошибок с `RestExceptionHandler`. Добавить Vitest-тесты API и компонентов: создание, поиск сборки, изменение/удаление элемента, отображение периода, flat-результат и состояния загрузки.

## Risks / Trade-offs

- **[Риск]** In-memory планы теряются при перезапуске процесса → **Митигирование:** явно сохранить ограничение в proposal и не обещать постоянство; PostgreSQL остаётся отдельным изменением.
- **[Риск]** Изменение состава спецификации после создания плана изменит результат flatten → **Митигирование:** зафиксировать в текущем контракте расчёт по актуальному `SpecificationService.flatten`; версионирование BOM не входит в этот change.
- **[Риск]** Большие планы вызывают много операций flatten → **Митигирование:** не добавлять преждевременное кэширование; покрыть корректность и оставить оптимизацию отдельным измеримым изменением.
- **[Риск]** UUID всё равно присутствуют в HTTP DTO для адресации → **Митигирование:** не показывать их в UI и не использовать поля ручного ввода; REST-контракт может адресовать ресурс UUID как существующие catalog endpoints.

## Open Questions

Нет: согласованные бизнес-правила и маршруты зафиксированы в спецификациях и решениях D1–D6.
