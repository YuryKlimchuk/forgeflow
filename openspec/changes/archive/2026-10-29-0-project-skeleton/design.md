# Design

## Context

См. `proposal.md` — Why. Репозиторий содержит документацию проекта и конфигурацию OpenSpec, но не содержит исходного Maven-каркаса. Архитектура должна сразу поддерживать Spring Modulith, DDD/Hexagonal-подход и строгие границы восьми модулей.

## Goals / Non-Goals

**Goals:**

- Зафиксировать единый корневой пакет и точку входа приложения.
- Представить каждый доменный контекст отдельным верхнеуровневым модулем Spring Modulith.
- Оставить модули пустыми, сохранив будущую структуру `api/application/domain/infrastructure`.
- Сделать граф зависимостей явным, минимальным и проверяемым автоматическим тестом.

**Non-Goals:**

- Реализация бизнес-сущностей, use case'ов, контроллеров, репозиториев и адаптеров.
- Настройка PostgreSQL, Flyway, Keycloak, веб-API и пользовательского интерфейса.
- Создание реализаций jMolecules-агрегатов или публичных прикладных контрактов.

## Decisions

### D1. Корневой пакет приложения

Использовать корневой пакет `com.forgeflow` и разместить `ForgeFlowApplication` непосредственно в нём. Это обеспечивает обнаружение всех верхнеуровневых пакетов-модулей и не вводит дополнительный технический модуль.

**Альтернатива:** размещать приложение в отдельном пакете `application`. Отклонено, поскольку это усложняет модель модулей и может сделать технический пакет самостоятельным модулем.

### D2. Структура модулей

Каждый модуль размещается как верхнеуровневый пакет под `com.forgeflow`, содержит `package-info.java` с `@ApplicationModule`, а также пустые `api`, `application`, `domain` и `infrastructure`. Пустые пакеты фиксируются минимальными `package-info.java`, если это требуется системой контроля версий или компилятором.

**Альтернатива:** создавать только корневые пакеты без слоёв. Отклонено, потому что следующий change получил бы неодинаковую структуру и неявные архитектурные границы.

### D3. Публичные контракты

Будущие межмодульные контракты размещаются только в `api`. Для пустого каркаса API-пакеты объявляются именованными интерфейсами Spring Modulith без добавления бизнес-типов. `application`, `domain` и `infrastructure` остаются внутренними.

**Альтернатива:** разрешать зависимость на весь модуль. Отклонено, поскольку это ослабляет границы и допускает случайный доступ к внутренним слоям.

### D4. Граф зависимостей

Задать белые списки: `adminpanel -> organizations`, `technology -> catalog, directories`, `specifications -> catalog, directories`, `catalog -> directories`, `security -> organizations`; `organizations`, `directories` и `shared` не зависят от других модулей. Эти зависимости отражают описанные предметные связи и не добавляют неподтверждённых связей.

`shared` остаётся независимым техническим основанием. На этом этапе другие модули не получают автоматическую зависимость от `shared`, пока не появится конкретный общий контракт.

### D5. Архитектурная проверка

Добавить `ModuleVerificationTest` на базе `ApplicationModules.of(ForgeFlowApplication.class).verify()`. Тест должен быть единственным обязательным стражем границ каркаса; документация диаграмм и функциональные тесты не входят в change.

### D6. Версии зависимостей

Использовать совместимые BOM/management-механизмы Spring Boot, Spring Modulith и jMolecules. Конкретная стабильная версия Spring Boot 4.1+ уточняется на этапе реализации по доступным совместимым релизам; proposal не фиксирует патч-версию.

## Risks / Trade-offs

- **[Риск]** Пустые Java-пакеты могут не сохраняться системой контроля версий. → **Митигировать:** использовать `package-info.java` для каждого требуемого пакета.
- **[Риск]** Выбранный граф зависимостей может потребовать уточнения при появлении первых контрактов. → **Митигировать:** изменять `allowedDependencies` отдельным OpenSpec change; не добавлять широкие зависимости заранее.
- **[Риск]** Spring Boot 4.1+ и версии Spring Modulith/jMolecules могут иметь ограничения совместимости. → **Митигировать:** проверить матрицу совместимости и зафиксировать совместимые версии в `pom.xml` до реализации.
- **[Компромисс]** Named interfaces без типов не дают функционального API, но намеренно сохраняют каркас пустым и не вводят неподтверждённые бизнес-правила.

## Migration Plan

Миграция существующего кода не требуется: проектный каркас создаётся с нуля. Откат выполняется удалением файлов реализации change до начала последующих функциональных changes.

## Open Questions

Нет вопросов, влияющих на данный scope; патч-версии зависимостей уточняются при реализации без изменения описанного поведения.
