# Design

## Context

Текущая `Organization` хранит имя, владельца через отдельный агрегат и участников; настройки организации отсутствуют. Пять application-сервисов каталога получают tenant через `OrganizationContext`, проверяют уникальность номера и создают сущность. REST-обработчик уже преобразует ошибки валидации и `IllegalArgumentException` в 400. Требование должно сохранить границы Spring Modulith и не создать цикл `organizations` ↔ `catalog`.

## Goals / Non-Goals

**Goals:**

- Хранить и заменять пять независимых опциональных паттернов на уровне организации.
- Проверять полное совпадение номера при создании всех пяти типов каталога.
- Валидировать regex до сохранения настроек и использовать существующую семантику HTTP 400.
- Сохранить tenant-изоляцию и совместимость организаций без заданных паттернов.

**Non-Goals:**

- Изменение номера существующего изделия или поведения `rename`.
- Зависимость `organizations.domain` от `catalog`.
- Исторические версии настроек, частичные обновления, массовое исправление существующих номеров или новые правила уникальности.

## Decisions

### D1. Настройки — value object модуля organizations

`OrganizationSettings` будет value object внутри `organizations.domain` с пятью опциональными полями `partNumberPattern`, `assemblyNumberPattern`, `buyNumberPattern`, `standartNumberPattern` и `vzkNumberPattern`. Он не будет ссылаться на типы `catalog`; это предотвращает обратную зависимость и цикл модулей. Пустое значение нормализуется как отсутствие ограничения на уровне проверки.

**Альтернатива:** хранить map по имени типа или enum каталога. Отклонено: это протащило бы каталог в домен организаций и ослабило типизированный контракт.

### D2. Настройки принадлежат агрегату Organization

`Organization` будет хранить текущий объект настроек и заменять его целиком. Репозиторий организаций получит операцию чтения настроек по `OrganizationId` (эквивалент `findSettings`). Если настройки не были установлены, порт возвращает пустые настройки или эквивалент отсутствия ограничений.

**Альтернатива:** отдельный агрегат/репозиторий настроек. Отклонено: настройки являются частью состояния организации и должны изменяться атомарно с ней.

### D3. Полная замена и проверка владельца в application-слое

Публичная операция `updateSettings(organizationId, settings)` выполняет проверку текущего subject на владельца, проверяет существование организации, валидирует все непустые regex и только затем заменяет объект и сохраняет организацию. Ошибка любой проверки не изменяет прежнее состояние.

**Альтернатива:** разрешить частичный PATCH. Отклонено согласованным бизнес-решением о полной замене.

### D4. Публичный provider в organizations.api

Модуль `organizations` опубликует новый порт чтения настроек, например `OrganizationSettingsProvider`, принимающий `OrganizationId` и возвращающий настройки. Его реализация будет собираться существующей application/infrastructure конфигурацией. `catalog` будет зависеть только от `organizations.api`; `organizations` не зависит от `catalog`.

**Альтернатива:** передавать настройки из web-слоя. Отклонено: это обходит доменный владелец tenant-контекста и дублирует логику между адаптерами.

### D5. Проверка в application-сервисах каталога

Каждый из пяти application-сервисов получает настройки по `OrganizationContext.requiredOrganizationId()` и проверяет только свой номер непосредственно перед проверкой дубликата/созданием. Проверка выполняется полным совпадением (`Pattern.matches()`), а номер сущности после создания не изменяется. `rename` не вызывает проверку номера.

**Альтернатива:** добавить regex-логику в каждую доменную сущность или repository. Отклонено: настройки внешнего агрегата и межмодульный provider не должны проникать в домен каталога или persistence-адаптер.

### D6. Контракт ошибок

Для несовпадения номера и некомпилируемого regex используется существующая цепочка 400 (`IllegalArgumentException` либо отдельное исключение, если это необходимо для ясности). Невалидный regex проверяется до изменения aggregate, поэтому частичного сохранения нет.

### D7. REST-операция настроек

HTTP-операция настроек будет добавлена в существующий REST-контракт организаций с DTO полной замены и доступом только владельца. Конкретный URL выбирается в соответствии с текущими маршрутами организаций и не меняет существующие маршруты каталога; ошибки авторизации и валидации используют существующий обработчик.

## Risks / Trade-offs

- **[Risk]** Регулярное выражение может быть вычислительно тяжёлым → использовать стандартный Java regex без расширения языка и не принимать некомпилируемые шаблоны; ограничения сложности regex в задачу не входят.
- **[Risk]** In-memory repository не отражает будущую persistent-схему → покрыть контракт repository/application тестами и не добавлять неподтверждённую миграцию PostgreSQL в текущий MVP.
- **[Risk]** Неправильная сборка provider может нарушить Modulith → добавить `ApplicationModules.verify()` в проверку и удерживать зависимость только из `catalog` в `organizations.api`.
- **[Trade-off]** Полная замена проще согласуется и атомарна, но клиент обязан передавать все пять полей; это принятое бизнес-решение.

## Migration Plan

Существующие организации получают пустые настройки, поэтому существующие непустые номера продолжают проходить. Сначала добавляются доменная модель и provider, затем application- и REST-операции; откат удаляет операцию и проверки, не требуя преобразования существующих каталожных записей.

## Open Questions

Нет: формат полей, права, семантика regex, область действия проверки и HTTP-статус согласованы.
