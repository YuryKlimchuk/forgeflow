# Proposal

## Why

Модуль `technology` пока содержит только архитектурный скелет и не имеет доменных типов, на которые смогут опереться будущие технологические процессы, операции и расчёт потребностей. Требуется зафиксировать минимальную доменную модель технологического процесса с привязкой к деталям каталога, не вводя прикладные сервисы, персистентность и фронтенд.

## What Changes

- Добавить в доменный слой модуля `technology` агрегат `TechnologyProcess` с jMolecules-аннотациями `@Entity` и `@Identity`.
- Добавить неизменяемый value object `Operation` (номер операции + наименование).
- Добавить публичный типизированный идентификатор `TechnologyProcessId` как `record` с `UUID value` и фабриками `generate()`/`of(UUID)`.
- Добавить driven port `TechnologyProcessRepository` (без Spring/JPA, tenant-scoped чтение, без физического удаления).
- Добавить чистый доменный сервис `TechnologyProcessService` для принуждения кросс-агрегатных правил: уникальность номера в организации и инвариант дефолтного процесса на деталь.
- Покрыть модель автоматизированными тестами (валидация, порядок операций, soft-delete, аудит, инвариант дефолтности).

## Capabilities

### New Capabilities

- `technology-domain-model`: доменные типы технологических процессов (агрегат, операция, порт репозитория, доменный сервис) и публичный идентификатор `TechnologyProcessId`.

### Modified Capabilities

Нет.

## Impact

Изменение затрагивает только пакеты `com.hydroyura.forgeflow.technology.api` и `com.hydroyura.forgeflow.technology.domain`, автоматизированные тесты домена technology и декларацию модуля `technology` (`technology/package-info.java`). Ссылка на деталь идёт только через `catalog.api.PartId`, организация — через `shared.api.OrganizationId`. Для корректного использования `shared.api.OrganizationId` декларация `@ApplicationModule` модуля technology расширяется разрешённой зависимостью `shared :: shared`: итоговый список — `catalog :: catalog`, `directories :: directories`, `shared :: shared`. Граф модулей остаётся ацикличным. База данных, Flyway-миграции, application-сервисы, REST-контроллеры и фронтенд не затрагиваются.

## Non-Goals

- Application-сервисы/use case'ы, REST-контроллеры, JPA-сущности, Flyway-миграции, PostgreSQL и фронтенд для technology.
- Storage-уровневый гарант уникальности номера: в этом change уникальность `number` в организации принуждается только доменным сервисом `TechnologyProcessService`. Частичный уникальный индекс `(organization_id, number) WHERE deleted_at IS NULL` и транзакционная обёртка регистрации обязательны при появлении персистентности (отдельный future change).
- Семантика дефолтности при логическом удалении дефолтного процесса: откладывается на отдельный future change. В текущем change `register`-guard может блокировать добавление нового процесса после удаления дефолтного — это принятый известный edge case.
- Привязка к сборочным единицам (`Assembly`) и прочим типам каталога.
- Оборудование, нормы времени, материалы, сортамент, единицы измерения и текстовое описание операций.
- Переупорядочивание существующих операций и перенос процесса на другую деталь.
- Валидация номера по паттерну организации (`OrganizationSettingsProvider`).
