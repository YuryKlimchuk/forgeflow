# Design

## Context

Текущий модуль `specifications` содержит только package-info-заглушки и уже объявлен зависимым от `catalog :: catalog` и `directories :: directories`. Каталог предоставляет типизированные идентификаторы, `AssemblyService.create(CreateAssemblyRequest)`, tenant-scoped application-сервисы и in-memory репозитории. Composition root собирает зависимости в `WebConfig`, а REST-адаптеры находятся в общем модуле `web` и используют `RestExceptionHandler`.

Детальная семантика поведения зафиксирована в delta-спеках `specifications`, `specifications-rest` и `frontend-catalog`.

## Goals / Non-Goals

**Goals:**

- Реализовать вертикальный срез от чистого домена до React UI без нарушения границ Spring Modulith.
- Сохранить `Specification` без собственного идентификатора: ключом агрегата является `AssemblyId` вместе с `OrganizationId`.
- Обеспечить проверяемую tenant-изоляцию и атомарные доменные правила строк.
- Сохранить существующие каталожные REST-маршруты и общий формат ошибок.

**Non-Goals:**

- PostgreSQL, Flyway и миграция in-memory данных.
- Разворачивание вложенных спецификаций, проверка косвенных циклов, версии, альтернативы, масса и единицы измерения кроме штук.
- Валидация существования, активности или tenant-принадлежности ссылочного элемента каталога при добавлении строки.

## Decisions

### D1. Идентичность агрегата

`Specification` будет отдельным агрегатом модуля `specifications`, но без `SpecificationId`. Его адрес — пара текущей `OrganizationId` и `AssemblyId`; пустой агрегат материализуется логически чтением нулевого набора строк. Альтернатива — отдельная сущность спецификации с UUID — отклонена, потому что создаёт вторую идентичность для уже существующей сборки.

### D2. Идентичность строки

Строка адресуется ссылкой на каталог (`CatalogItemType` + соответствующий типизированный id), без row-id. Дискриминированная ссылка позволит различать `PartId`, `AssemblyId`, `BuyId`, `StandartId` и `VzkId`, а уникальность ссылки естественно обеспечивает максимум одну строку элемента. Альтернатива — UUID строки — отклонена как лишний идентификатор и усложнение REST-адресации.

### D3. Богатая доменная модель

В `specifications.domain` будут размещены агрегат, value objects для положительного количества и ссылки каталога, репозиторный порт и доменные исключения. Домен не будет зависеть от Spring, JPA или REST; jMolecules-аннотации применяются по образцу `catalog` и `organizations`. Проверка прямой самоссылки и уникальности выполняется внутри агрегата.

### D4. Межмодульная граница каталога

При `copy` application-сервис спецификаций вызывает только `catalog.api.AssemblyService.create(CreateAssemblyRequest)` в текущем tenant-контексте. `addRow`, `removeRow`, `changeQuantity` и `get` каталог не вызывают: ссылка сохраняется как дискриминированное значение. Для копирования исходная сборка и строки читаются через публичные контракты спецификаций, а создание новой сборки выполняется через публичный API каталога.

### D5. Application API

Публичный API модуля содержит tenant-scoped операции `addRow`, `removeRow`, `changeQuantity`, `get` и `copy`, а также неизменяемые request/view-типы. Application-сервис получает `OrganizationId` только из `OrganizationContext.requiredOrganizationId()` и передаёт его в repository-операции. Отсутствующая сборка/строка представляется отдельными исключениями модуля.

### D6. Persistence и composition root

Используется in-memory репозиторий по образцу `InMemoryPartRepository`; ключ хранения включает организацию и `AssemblyId`, а операции выполняют фильтрацию по tenant. Реализации репозитория и application-сервиса регистрируются в `WebConfig`. PostgreSQL/Flyway не добавляются, поскольку это отдельный последующий change.

### D7. REST-маршруты

Добавляется тонкий `SpecificationController` в `web` с маршрутами:

- `GET /api/v1/specifications/{assemblyId}/rows`;
- `POST /api/v1/specifications/{assemblyId}/rows`;
- `PUT /api/v1/specifications/{assemblyId}/rows`;
- `DELETE /api/v1/specifications/{assemblyId}/rows`;
- `POST /api/v1/specifications/{sourceAssemblyId}/copy`.

PUT и DELETE адресуют строку телом дискриминированной ссылкой, поскольку row-id отсутствует. `web/package-info.java` получает разрешение зависимости от `specifications :: specifications`; существующие каталожные пути не меняются.

### D8. Ошибки REST

Новые исключения спецификаций добавляются в существующий `RestExceptionHandler`: отсутствие ресурса → 404/not_found, дубликат элемента → 409/duplicate, ошибки аргументов и доменной валидации → 400/bad_request. Существующие обработчики и статусы каталога сохраняются без изменения семантики.

### D9. UI-интеграция

В `frontend/src/api.ts` добавляется отдельный типизированный клиент спецификаций рядом с `CATALOG_TYPES`, а UI получает блок состава для выбранной сборки и форму копирования. Используются существующие `ApiClientError`, `humanizeError`, React/Vite и Vitest. Элементы каталога для выбора могут отображаться как типизированные ссылки; фильтрация tenant/active остаётся ответственностью UI-каталога, сервер спецификаций не выполняет такую проверку.

## Risks / Trade-offs

- **[Риск]** In-memory хранилище теряет спецификации при перезапуске → явно ограничить change и покрыть контракт тестами, не обещая долговременную сохранность.
- **[Риск]** Строка может ссылаться на удалённый или чужой элемент каталога → это согласованное поведение ссылочного слоя; добавить проверку существования только отдельным изменением после согласования.
- **[Риск]** Копирование создаёт сборку, после чего сохранение строк может завершиться ошибкой → application-сервис должен выполнять операции в определённом порядке и тестировать отсутствие частичного результата; транзакционность между in-memory репозиториями не заявляется.
- **[Риск]** REST PUT/DELETE с телом строки менее удобен для клиентов → это следствие отсутствия row-id; единая ссылка на каталог сохраняет доменную адресуемость.
- **[Риск]** Изменение `web/package-info.java` может выявить архитектурные нарушения → добавить `ApplicationModules.verify()` в проверочный набор и использовать только публичные API.

## Open Questions

Нет: оставшиеся ограничения и отложенные возможности зафиксированы в non-goals и delta-спеках.
