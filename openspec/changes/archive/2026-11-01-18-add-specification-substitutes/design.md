# Design

## Context

Текущая спецификация хранит строки в агрегате `Specification`, где `SpecificationRow` является record без собственного идентификатора. Репозиторий и application-сервис работают in-memory с tenant-ключом организации и сборки. Каталог уже предоставляет API-сервисы для сборок и деталей, а прямые ссылки строк принимаются без проверки состояния каталога. REST-контроллер спецификаций является тонким адаптером, frontend загружает каталог единым индексом и отображает строки в `SpecificationDetail`.

## Goals / Non-Goals

**Goals:**

- Добавить независимое tenant-scoped хранение замен с адресацией `(OrganizationId, AssemblyId, CatalogItemReference основной строки)`.
- Сохранить value-object модель `SpecificationRow`, текущую уникальность основной позиции и существующие контракты строк, расширив view только новым признаком.
- Обеспечить каскад и копирование замен на уровне application-операций.
- Использовать только существующие API каталога и не создавать межмодульные зависимости вне API-пакетов.
- Покрыть доменные, application, REST и frontend сценарии автоматизированными тестами.

**Non-Goals:**

- Добавление постоянной БД или Flyway-миграции: текущая реализация спецификаций in-memory.
- Выбор активного заменителя, приоритеты, условия применения и рекурсивное разрешение замен.
- Изменение алгоритма `flatten`.

## Decisions

### D1. Отдельный агрегат и репозиторий замен

`Substitution` хранит `OrganizationId`, `AssemblyId`, основную `CatalogItemReference` и множество ссылок заменителей; репозиторий адресует агрегат составным ключом `(OrganizationId, AssemblyId, item)`. Это сохраняет `SpecificationRow` без id и не нарушает правило «один элемент = одна строка». Альтернатива — добавить список замен в `SpecificationRow` — отклонена, поскольку меняет value object и усложняет каскадное хранение.

### D2. Доменная валидация без обращения к каталогу

Агрегат проверяет только типы, самозамену и дубликат. Проверка существования каталожного объекта не выполняется, чтобы сохранить установленное правило прямых ссылок спецификации. Для определения ошибки строки application сначала проверяет наличие основной строки в `Specification`; это также предотвращает создание замены для отсутствующей строки.

### D3. Хранение и жизненный цикл

In-memory репозиторий замен хранит tenant-изолированные карты. `removeRow` удаляет соответствующий aggregate substitutions после успешного удаления строки. `copy` переносит ссылки заменителей вместе с каждой строкой в новую сборку, не создавая новых ссылок каталога и не копируя замены, не связанные с исходными строками.

### D4. Контракт REST

Для операций используется общий ресурс `/api/v1/specifications/{assemblyId}/substitutes`; основная ссылка передаётся в query для GET и в JSON для POST/DELETE. POST возвращает созданную ссылку со статусом 201, DELETE — 204. В `SpecificationRowView` добавляется `hasSubstitutes`, поэтому существующий GET строк сохраняет поля `item` и `quantity` и получает обратно совместимое расширение JSON.

### D5. Ограничение типов в UI

Список кандидатов для замены формируется из уже загруженного каталожного индекса только для типа основной строки и только для `PART`/`ASSEMBLY`. Форма не содержит количества: количество наследуется основной строкой. Модалка не содержит операции выбора дефолта.

### D6. Seed-формат

Seed-строка расширяется необязательным списком ссылок заменителей, каждая ссылка задаётся `type` и `number`. `DataSeeder` сначала создаёт строки, затем разрешает seed-ссылки через уже построенный индекс и сохраняет отдельные замены. Это позволяет сохранять `seed-data/specifications.json` человекочитаемым и согласованным с существующим форматом.

## Risks / Trade-offs

- **[Риск]** In-memory замены теряются при перезапуске, как и текущие строки спецификаций. → Seed загружает демонстрационные данные; постоянное хранение не входит в этот change.
- **[Риск]** Ссылка заменителя может указывать на отсутствующий или изменённый каталоговый объект. → Это намеренно соответствует текущему правилу прямых ссылок; UI показывает недоступный объект как неразрешённый, а домен не выполняет каталоговую проверку.
- **[Риск]** Query-представление основной ссылки усложняет ручные REST-вызовы. → Контракт фиксирует имена `itemType` и `itemId`, а UI скрывает UUID и формирует запрос типизированным клиентом.
- **[Риск]** Добавление поля в `SpecificationRowView` требует обновления существующих frontend fixture и тестов. → Обновить типы, mock-ответы и проверки JSON в рамках одной задачи.

## Migration Plan

Изменение не требует миграции данных: хранилище in-memory создаётся с пустым набором замен, а seed загружает демонстрационные замены при старте. Откат выполняется возвратом версии приложения; отдельной схемы БД или миграции нет.

## Open Questions

Нет: все решения, влияющие на контракт и объём, зафиксированы в proposal и delta-specs.
