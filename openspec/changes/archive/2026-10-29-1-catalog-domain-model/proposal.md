# Proposal

## Why

Модуль `catalog` пока содержит только архитектурный скелет и не имеет доменных типов, на которые смогут опираться будущие спецификации, технологические процессы и расчёт потребностей. Сейчас необходимо зафиксировать минимальную предметную модель каталога: пять различимых типов изделий с типизированными идентификаторами, не вводя неподтверждённые свойства и бизнес-правила.

## What Changes

- Добавить в доменный слой модуля `catalog` пять сущностей: `Assembly`, `Part`, `Buy`, `Standart` и `Vzk`.
- Пометить каждую сущность jMolecules-аннотациями `@Entity` и `@Identity`.
- Ограничить каждую сущность единственным полем — типизированным ID соответствующего типа.
- Добавить пять ID как Java `record` с компонентом `UUID value` и фабриками `generate()` и `of(...)`.
- Разместить ID в публичном API-пакете `catalog`, поскольку типы идентификаторов являются потенциальными межмодульными контрактами; сущности оставить в `domain`.
- Не добавлять поля кроме ID, бизнес-логику, репозитории, use case'ы, инфраструктуру, миграции или прикладные API.

## Capabilities

### New Capabilities

- `catalog-domain-model`: минимальные доменные сущности каталога и типизированные идентификаторы для пяти видов изделий.

### Modified Capabilities

Нет.

## Impact

Изменение затрагивает только исходные пакеты `com.forgeflow.catalog.api` и `com.forgeflow.catalog.domain`, а также автоматизированные тесты доменной модели. Межмодульный граф не изменяется: модуль `catalog` сохраняет существующую зависимость от `directories`. Базы данных, публичные use case-контракты, репозитории и инфраструктурные адаптеры не затрагиваются.
