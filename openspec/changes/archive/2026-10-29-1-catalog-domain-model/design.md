# Design

## Context

См. `proposal.md` — Why. Модуль `catalog` уже имеет пакеты `api`, `application`, `domain` и `infrastructure`, корневую декларацию `@ApplicationModule` и зависимость `directories :: directories`. Изменение должно сохранить чистый домен без зависимостей от Spring, хранилища и внешних интеграций.

## Goals / Non-Goals

**Goals:**

- Представить пять видов изделий отдельными минимальными сущностями.
- Сделать идентификаторы типобезопасными и пригодными для межмодульных ссылок.
- Сохранить текущие границы Spring Modulith и направленный граф зависимостей.
- Обеспечить проверяемость структуры, аннотаций и минимальности модели.

**Non-Goals:**

- Определение атрибутов изделий, способов получения, статусов или иных бизнес-правил.
- Создание репозиториев, use case'ов, событий, контроллеров, миграций и адаптеров.
- Реализация операций создания, изменения, поиска или публикации сущностей.

## Decisions

### D1. Пять отдельных сущностей

Создать `Assembly`, `Part`, `Buy`, `Standart` и `Vzk` как отдельные сущности, каждую в собственном подпакете `com.forgeflow.catalog.domain.<name>` (например, `com.forgeflow.catalog.domain.assembly`). Такое разделение отражает текущую предметную классификацию каталога и не смешивает тип объекта со способом получения: будущая модель сможет независимо описывать эти понятия, не вводя их сейчас.

**Альтернатива:** единая сущность `Product` с признаком типа. Отклонено, поскольку это заранее фиксирует объединённую модель и затрудняет явное различение групп ВЗК и видов изделий.

### D2. Минимальный состав сущностей

Каждая сущность будет содержать только одно поле идентификатора соответствующего типа и не будет иметь поведения за пределами конструктора/создания, необходимого для формирования валидного объекта. jMolecules `@Entity` и `@Identity` фиксируют DDD-смысл типов и позволяют архитектурным тестам проверять модель.

**Альтернатива:** сразу добавить названия, tenant ID, способ получения или ссылки на связанные сущности. Отклонено: эти сведения не заданы задачей и относятся к последующим изменениям.

### D3. Типизированные ID как records

Для каждой сущности создать отдельный record `*Id` с компонентом `UUID value`, статическими фабриками `generate()` и `of(UUID)`. Record обеспечивает неизменяемость и value-based equality, а отдельный тип предотвращает смешивание идентификаторов разных сущностей.

**Альтернатива:** использовать `UUID` непосредственно в сущностях или общий `EntityId`. Отклонено, потому что это теряет типобезопасность на границах модулей и не соответствует требованию отдельных типизированных ID.

### D4. Размещение ID в `api`

Разместить `AssemblyId`, `PartId`, `BuyId`, `StandartId` и `VzkId` в `com.forgeflow.catalog.api`, а сущности — в собственных подпакетах `com.forgeflow.catalog.domain.<name>`. Это решение следует конвенции `spring-modulith-module`: типизированные ID являются публичными контрактами, если на них должны ссылаться соседние модули; внутренние сущности остаются скрытыми в domain.

**Альтернатива:** разместить ID рядом с сущностями в `domain`. Отклонено, поскольку будущие `specifications` и `technology` должны ссылаться на изделия только через публичные ID, не нарушая границы модулей.

### D5. Граница публичного API

ID будут добавлены в уже объявленный named interface `com.forgeflow.catalog.api` (`@NamedInterface("catalog")`). Новые отдельные named interfaces и изменения `allowedDependencies` не требуются: текущий контракт уже предоставляет публичный API каталога.

### D6. Проверка

Добавить unit/архитектурные проверки, которые подтверждают наличие пяти сущностей, jMolecules-аннотаций, единственного поля ID, record-ID с `UUID` и фабриками, а также отсутствие репозиториев и use case'ов. Существующая модульная проверка должна продолжить проходить без изменения графа.

## Risks / Trade-offs

- **[Риск]** Название `Standart` может отличаться от нормативного английского `Standard`, но оно задано предметной задачей. → **Митигировать:** зафиксировать точное имя во всех контрактах и не переименовывать без отдельного change.
- **[Риск]** Размещение ID в публичном API расширяет поверхность модуля до появления реальных межмодульных сценариев. → **Митигировать:** публиковать только неизменяемые ID, не раскрывая сущности и внутренние слои.
- **[Риск]** Фабрика `of(UUID)` может получить `null`. → **Митигировать:** при реализации обеспечить проверку входного UUID и покрыть её тестом, не добавляя иных бизнес-правил.
- **[Компромисс]** Сущности без прикладного поведения являются намеренно неполными заготовками; это снижает текущую функциональность, но предотвращает преждевременную фиксацию модели.

## Migration Plan

Миграция данных не требуется: постоянное хранение и миграции базы данных не входят в change. Откат выполняется удалением добавленных ID, сущностей и тестов; существующий каркас модуля остаётся неизменным.

## Open Questions

Нет вопросов, влияющих на scope или архитектурное решение. Поля сущностей и операции над ними должны быть предметом последующих отдельных changes.
