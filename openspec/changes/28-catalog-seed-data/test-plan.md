# Test plan — «Демо-данные каталога и спецификаций» (change `28-catalog-seed-data`)

> Этап QA Planning (G4). Независимая оценка решения Architect для data-only изменения:
> правка `seed.sql` (секции `part`, `assembly`, `specification_row`, `substitution` и два поля
> паттернов организации) + дельты main-спеков `organizations` и `specifications`.
> Документ — контракт проверки для G7. Артефакты на русском языке. Findings и статус G4 — в отчёте
> сабагента; здесь — резюме в разделах «Risks & assumptions» и «Entry/exit criteria».

## 1. Scope & goals

Проверяем перенос демо-каталога и демо-спецификаций из сквозных примеров
`docs/user-guide/catalog/examples.md` в идемпотентный `seed.sql`, а также актуализацию двух
main-спеков. Код приложения, схема БД и Flyway-миграции **не меняются**; `seed.sql` по-прежнему
выполняется пользователем вручную после миграций.

Цели:

- подтвердить соответствие данным требованиям R1–R8 и 12 AC (Analyst, G2);
- проверить контрольные суммы: 24 детали, 19 сборок, 100 строк спецификаций
  (ASSEMBLY=17, PART=43, VZK=40, BUY=0, STANDART=0), 1 замена;
- проверить дословность переноса номеров/наименований/составов/количеств (R1);
- проверить целостность ссылок (нет висячих UUID) и идемпотентность двойного прогона;
- проверить неизменность секций `buy`/`standart`/`vzk` (обе части)/`material`/`sortament`/`owner`;
- зафиксировать риски тестируемости/надёжности решения (см. findings).

**Вне scope (non-goals):** изменение кода/мапперов/REST/Flyway/схемы; удаление legacy-строк
`ВЗК-0001…ВЗК-0050`; правка иллюстративных номеров `Д-0001`/`Д-0002` в сценариях
`planning`/`frontend-catalog`/`specifications` (сортировка); автоматическая загрузка `seed.sql`
приложением; очистка ранее засеянных локальных БД.

## 2. Test levels

Data-only изменение ⇒ основная проверка — SQL на свежей БД. Пирамида применима частично.

| Уровень | Что покрывает | Инструменты |
|---|---|---|
| **Static / file-level** | Отсутствие `Д-\d{4}`/`СБ-\d{4}` в изменяемых секциях; точные счётчики строк INSERT; уникальность детерминированных UUID; побайтовая неизменность незатронутых секций | `grep`/`diff`/скрипт, `git diff -- seed.sql` |
| **Unit (рекомендуется)** | `OrganizationSettings.matches*` с новыми паттернами (AC-4, негативные/граничные случаи). Опционально: `SpecificationApplicationService.flatten` на сокращённой in-memory цепочке `00.000→00.101/00.102/00.103→15.130→30.001` для подтверждения qty=4 (AC-8, алгоритм) | JUnit 5 + AssertJ, без Spring |
| **Slice / integration (рекомендуется, F1)** | `SeedSqlVerificationTest`: Testcontainers PostgreSQL → Flyway `V1…V8` → выполнение `seed.sql` → SQL-asserts (счётчики, `GROUP BY item_type`, висячие ссылки, идемпотентность двойного прогона) | Testcontainers + Spring JDBC/`JdbcTemplate`/`ResourceDatabasePopulator` |
| **Manual SQL (текущий путь по A5)** | То же, что в slice-уровне, но вручную через `psql` на свежей БД | `psql` + `SELECT` |

Если автоматизированный slice-тест (F1) принят, ручные проверки остаются контрольной
верификацией; если нет — ручные проверки являются основным источником G7-доказательств.

## 3. Test scenarios

Идентификаторы: `P*` — positive, `N*` — negative, `B*` — boundary.

### 3.1 Positive

- **P1 Счётчик деталей (AC-1).** `SELECT count(*) FROM part WHERE organization_id='…01'` = 24;
  среди `number` нет ни одного `Д-`.
- **P2 Счётчик сборок (AC-2).** `count(*) FROM assembly` = 19; среди `number` нет `СБ-`.
- **P3 Дословность номеров и наименований (R1).** Множество `(number, name)` из `part` и
  `assembly` ровно совпадает с эталонными списками `examples.md`:
  - 12 деталей RGS (`30.001…30.006`, `40.001…40.006`) + 12 деталей NAS;
  - 13 сборок RGS + 6 сборок NAS (включая `RGS.100-000.00.100-01 СБ`).
- **P4 Паттерны организации (AC-3).** Чтение строки `organization` демо-организации возвращает
  ровно пять паттернов: `part`=`(RGS|NAS)\.100-000\.\d{2}\.\d{3}`,
  `assembly`=`(RGS|NAS)\.100-000\.\d{2}\.\d{3}(-\d{2})? СБ`, `buy`=`ПОК-\d{4}`,
  `standart`=`СТ-\d{4}`, `vzk`=`VKZ\.\d{3}-\d{3}\.\d{2}\.\d{3}`.
- **P5 Полное совпадение номеров с паттернами (AC-4).** Все 24 номера деталей дают
  `matchesPart=true`; все 19 номеров сборок (включая `RGS.100-000.00.100-01 СБ`) дают
  `matchesAssembly=true`. Проверяется unit-тестом на `OrganizationSettings` (в PostgreSQL POSIX-regex
  `\d` не является символьным классом, поэтому точная проверка семантики — в Java).
- **P6 Распределение строк спецификации (AC-5).** `SELECT item_type, count(*) FROM
  specification_row WHERE organization_id='…01' GROUP BY item_type` даёт `ASSEMBLY`=17, `PART`=43,
  `VZK`=40, `BUY`=0, `STANDART`=0; сумма = 100.
- **P7 Состав головы (AC-6).** Спецификация `RGS.100-000.00.000 СБ` = ровно 9 прямых строк:
  5 `ASSEMBLY` (`00.101`×1, `00.102`×2, `00.103`×1, `00.115`×1, `00.120`×1) + 4 `VZK`
  (`VKZ.010-000.00.002`×4, `VKZ.025-000.00.002`×4, `VKZ.030-000.00.002`×4,
  `VKZ.005-000.00.003`×4).
- **P8 Дублируемые составы (AC-7).** Прямые строки сборки `RGS.100-000.00.100-01 СБ` равны
  строкам `RGS.100-000.00.100 СБ`; `RGS.100-000.00.120 СБ` = `RGS.100-000.00.115 СБ`;
  `NAS.100-000.00.120 СБ` = `NAS.100-000.00.110 СБ` (сравнение по `item_type`+`item_id`+`quantity`).
- **P9 Flat BOM головы (AC-8).** `flatten(RGS.100-000.00.000 СБ)` содержит лист
  `RGS.100-000.30.001` с итоговым количеством `4` (вклад `00.101`×1 + `00.102`×2×1 + `00.103`×1).
- **P10 Единственная замена (AC-9).** `substitution` содержит ровно 1 запись:
  head=`RGS.100-000.00.000 СБ`, item=`ASSEMBLY` `RGS.100-000.00.102 СБ`,
  substitute=`ASSEMBLY` `RGS.100-000.00.100-01 СБ`; чтение спецификации головы возвращает для
  строки `00.102 СБ` значение `hasSubstitutes=true`.
- **P11 Отсутствие висячих ссылок (AC-10).** Каждый `assembly_id`, `item_id` из
  `specification_row` и `assembly_id`/`item_id`/`substitute_id` из `substitution` разрешается в
  существующий UUID `part`/`assembly`/`vzk` той же организации (`LEFT JOIN` → нет `NULL`).
- **P12 Идемпотентность (AC-11).** Двойной прогон `seed.sql` на свежей БД: те же `count(*)`
  (part=24, assembly=19, specification_row=100, substitution=1), без ошибок ограничений/дубликатов.
- **P13 Неизменность остальных секций (AC-12).** `git diff`/сравнение показывает изменения только
  в секциях `-- part`, `-- assembly`, `-- specification_row`, `-- substitution` и двух полях
  `INSERT INTO organization`; `-- buy`, `-- standart`, `-- vzk` (обе части), `-- material`,
  `-- sortament`, `-- owner` — побайтово прежние.
- **P14 VZK-ссылки на `VKZ.xxx` (R5, D7).** Все 40 строк `VZK` ссылаются ровно на 13 различных
  позиций, чьи `number` соответствуют `VKZ\.\d{3}-\d{3}\.\d{2}\.\d{3}`; ни одна не ссылается на
  legacy `ВЗК-xxxx` (важно: legacy UUID остаются в первой секции `-- vzk`, поэтому проверка —
  по `number`, а не только по существованию UUID).
- **P15 Неиспользуемые позиции (D9).** Ровно две детали не входят ни в одну спецификацию:
  `RGS.100-000.40.001` (Кольцо упорное) и `NAS.100-000.40.006` (Штифт); остальные 22 детали
  используются хотя бы в одной строке. (Опционально-строгое: distinct `ASSEMBLY`-позиций = 13.)
- **P16 Глубина BOM (delta specs/specifications).** Существуют цепочки глубиной от 3 до 4 уровней,
  заканчивающиеся `PART` или `VZK`: например `00.000→00.102→15.130→30.002` (4 уровня) и
  `00.000→00.115→40.003` (3 уровня); цепочек глубже 4 нет.

### 3.2 Negative

- **N1 Старые номера удалены.** В файле `seed.sql` нет ни `Д-\d{4}` в `-- part`, ни `СБ-\d{4}`
  в `-- assembly`.
- **N2 Нет `BUY`/`STANDART`.** В `specification_row` отсутствуют `item_type IN ('BUY','STANDART')`.
- **N3 Уникальность UUID.** Новые 24+19 детерминированных UUID уникальны между собой и не
  пересекаются с существующими UUID в `seed.sql` (включая две секции `-- vzk`, `material`,
  `sortament`, `owner`).
- **N4 Кодирование `item_type`.** Все значения `item_type`/`substitute_type` — заглавные
  `ASSEMBLY`/`PART`/`VZK`; нет строчных или произвольных строк.
- **N5 VZK ≠ legacy.** Ни одна `VZK`-строка `specification_row` не ссылается на UUID из первой
  секции `-- vzk` (legacy `ВЗК-xxxx`).
- **N6 Удалены старые замены.** В `substitution` нет строк, отличных от единственной записи из P10
  (старые две записи удалены из файла).
- **N7 Положительные количества.** Все `quantity` в `specification_row` — положительные целые
  (`>= 1`).

### 3.3 Boundary

- **B1 Опциональный суффикс сборки.** `RGS.100-000.00.100-01 СБ` проходит `matchesAssembly`
  (ветвь `(-\d{2})?`); `RGS.100-000.00.100 СБ` тоже проходит.
- **B2 Различение part/assembly полным совпадением.** `RGS.100-000.00.100` (без ` СБ`) даёт
  `matchesPart=true`, но `matchesAssembly=false`.
- **B3 Старые номера не проходят новые паттерны.** `Д-0001` → `matchesPart=false`;
  `СБ-0001` → `matchesAssembly=false`.
- **B4 Некорректные номера отклоняются.** Трейлинг-пробел (`…100 СБ `), однозначная группа
  (`…0.100 СБ`), двухзначная позиция (`…00.10 СБ`) → `matchesAssembly=false`.
- **B5 Литералы паттернов без потери экранов.** `SELECT part_number_pattern, assembly_number_pattern`
  возвращает байт-в-байт строки из D5/P4 (при `standard_conforming_strings=on` `\.`/`\d` сохраняются
  как есть).

## 5. Environment & data

- **БД:** PostgreSQL (локально или Testcontainers `postgres:17`), Flyway-миграции `V1…V8`
  применены, **свежая схема без ранее засеянных данных** (критично: см. риск R-A).
- **Скрипт:** корневой `seed.sql` выполняется после миграций; для AC-11 — дважды подряд.
- **Java (для unit/опц. slice):** Java 25, Maven, JUnit 5 + AssertJ (+ Mockito для flatten),
  Testcontainers + Spring `JdbcTemplate`/`ResourceDatabasePopulator` для slice-теста.
- **Источник истины:** `docs/user-guide/catalog/examples.md` (эталон номеров/наименований/составов/
  количеств).
- **Демо-организация:** `00000000-0000-0000-0000-000000000001`; владелец
  `00000000-0000-0000-0000-000000000002`; пользователь `…000010` (без изменений).
- **Ожидаемые эталонные значения:** 24 детали (12 RGS + 12 NAS), 19 сборок (13 RGS + 6 NAS),
  100 строк спецификаций (17/43/40/0/0), 1 замена; 13 различных VZK-позиций; 2 неиспользуемые
  детали; глубина BOM 3–4.

## 6. Risks & assumptions

**Assumptions (принятые G2/G3):** `seed.sql` не выполняется приложением и не загружается
интеграционными тестами (A5 — оспорено в F1); верификация — на свежей БД; детерминированные
UUID генерируются name-based; `item_type` — заглавные `CatalogItemType.name()`; regex хранится как
литерал при `standard_conforming_strings=on`.

**Риски:**

- **R-A Проверка валидна только на свежей БД.** На уже засеянной БД `ON CONFLICT DO NOTHING` не
  удалит старые `Д-*`/`СБ-*` и не обновит паттерны организации ⇒ AC-1/AC-2/AC-3 не выполнятся.
  Митигация: среда G7 — свежая БД (Flyway → `seed.sql`), ограничение задокументировано в D10/non-goals.
- **R-B Полностью ручная проверка (A5) не даёт регрессионной защиты.** Data-only изменение без
  автоматизированного теста легко регрессирует. Митигация: F1 — добавить `SeedSqlVerificationTest`
  (Testcontainers). Не меняет production-поведение.
- **R-C Потеря экранов в regex-литералах.** При неверных настройках `standard_conforming_strings`
  `\.`/`\d` могут потерять бэкслеш. Митигация: B5 (байт-в-байт сверка паттернов) + P5 (Java-семантика).
- **R-D Частичное покрытие R1.** AC не проверяют дословность наименований и VZK-ссылки на `VKZ.xxx`.
  Митигация: добавлены сценарии P3/P14 (см. F2/F3).
- **R-E Паттерн part — префикс паттерна assembly.** Номер сборки без ` СБ` формально проходит
  `matchesPart`. Это следствие заданных в R4 паттернов, не дефект; зафиксировано в B2 (F5).
- **R-F Глубина BOM в delta-спеке без AC.** Требование «глубина 3–4» не покрыто G2-AC.
  Митигация: добавлен сценарий P16 (F4).
- **R-G Коллизии детерминированных UUID.** Митигация: namespace включает тип и полный номер;
  N3 проверяет уникальность среди новых и существующих UUID.
- **R-H Иллюстративные `Д-`/`СБ-` в main-спеках.** Сценарии сортировки в `planning`,
  `frontend-catalog` и `specifications` («Сортировка плоского состава») сохраняют номера
  `Д-0001`/`Д-0002` — это иллюстрации, не seed-данные (non-goal); корректность не нарушают.

## 7. Entry/exit criteria

**Entry (условия начала реализации, G4→G5):**

- [x] Артефакты Architect на месте: `proposal.md`, `specs/`, `design.md`, `tasks.md`.
- [x] `openspec validate 28-catalog-seed-data` — valid.
- [x] Блокирующих находок нет (F1 — рекомендация по автоматизации, не блокирует; F2–F4 закрыты
  добавлением сценариев в этот план; F5 — принятый риск).
- [ ] Зафиксировано решение пользователя по F1 (автоматизировать SQL-проверки Testcontainers-тестом
  либо оставить ручную проверку по A5).
- [ ] Test plan утверждён пользователем (G4).

**Exit (G7 pass criteria):**

- [ ] Все сценарии P1–P16, N1–N7, B1–B5 выполнены и прошли (`PASSED`).
- [ ] Контрольные суммы подтверждены: part=24 (без `Д-`), assembly=19 (без `СБ-`),
      specification_row=100 (17/43/40/0/0), substitution=1.
- [ ] Составы дублируемых сборок совпадают (AC-7); flatten `00.000 СБ` даёт `30.001` qty 4 (AC-8).
- [ ] Нет висячих ссылок и дубликатов UUID; `VZK` ссылается только на `VKZ.xxx` (AC-10/R5).
- [ ] Двойной прогон `seed.sql` без дубликатов и ошибок ограничений (AC-11).
- [ ] Незатронутые секции побайтово идентичны прежней версии (AC-12).
- [ ] Дельта-спеки `organizations`/`specifications` согласованы; `openspec validate` зелёный.
- [ ] Если добавлены unit/Testcontainers-тесты (F1) — `mvn test` зелёный, включая
      `ModuleVerificationTest` (`ApplicationModules.verify()`).
- [ ] Нет незакрытых дефектов уровня blocker/major.

**Fail-условия:** любое расхождение счётчиков/составов/паттернов, наличие `Д-`/`СБ-`/`ВЗК-`-ссылок
в изменяемых секциях, висячие UUID, дубликаты после второго прогона, изменение незатронутых секций,
незакрытые blocker/major findings → возврат к Developer (после правок — повторный Reviewer и QA Testing).
