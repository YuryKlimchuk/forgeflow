# catalog-all-types Specification

## Purpose
Предоставляет единый application-контракт для создания, просмотра, переименования и логического удаления Assembly, Buy, Standart и Vzk в пределах текущей организации.

## Requirements

### Requirement: Сервис каждого дополнительного типа
Каталог SHALL предоставлять отдельный публичный сервис для `Assembly`, `Buy`, `Standart` и `Vzk` с операциями create, get, list, rename и delete.

#### Scenario: Вызов сервиса типа
- **WHEN** клиент вызывает любую поддержанную операцию для типа каталога
- **THEN** операция выполняется через публичный API соответствующего типа

### Requirement: Создание дополнительного типа
Каждый сервис SHALL создавать активную сущность с уникальным в организации номером и SHALL отклонять номер, не соответствующий заданному паттерну организации; при отсутствии паттерна SHALL разрешать любой непустой номер.

#### Scenario: Создание новой записи
- **WHEN** текущая организация установлена и переданы непустые `number` и `name`, а номер свободен
- **THEN** сервис возвращает созданную запись с новым идентификатором

#### Scenario: Дубликат номера
- **WHEN** активная запись того же типа с таким номером уже принадлежит организации
- **THEN** сервис отклоняет создание ошибкой конфликта и не сохраняет новую запись

#### Scenario: Создание Assembly по паттерну
- **WHEN** для организации задан `ASM-[0-9]+` и передан свободный номер `ASM-7`
- **THEN** сервис Assembly создаёт активную запись

#### Scenario: Создание Buy по паттерну
- **WHEN** для организации задан паттерн Buy и передан соответствующий свободный номер
- **THEN** сервис Buy создаёт активную запись

#### Scenario: Создание Standart по паттерну
- **WHEN** для организации задан паттерн Standart и передан соответствующий свободный номер
- **THEN** сервис Standart создаёт активную запись

#### Scenario: Создание Vzk по паттерну
- **WHEN** для организации задан паттерн Vzk и передан соответствующий свободный номер
- **THEN** сервис Vzk создаёт активную запись

#### Scenario: Номер не соответствует паттерну
- **WHEN** номер любого из четырёх типов не соответствует заданному паттерну его типа
- **THEN** соответствующий сервис отклоняет создание ошибкой клиентской валидации и не сохраняет запись

#### Scenario: Паттерн не задан
- **WHEN** паттерн типа отсутствует или пуст
- **THEN** любой непустой номер, не являющийся дубликатом, принимается

### Requirement: Чтение дополнительных типов
Каждый сервис SHALL возвращать только активные записи текущей организации, а список SHALL быть отсортирован по `number` по возрастанию.

#### Scenario: Изоляция списка
- **WHEN** организация запрашивает список своего типа
- **THEN** результат не содержит удалённых записей и записей другой организации

### Requirement: Переименование дополнительного типа
Каждый сервис SHALL переименовывать существующую активную запись текущей организации и сохранять результат.

#### Scenario: Успешное переименование
- **WHEN** передан идентификатор активной записи и непустое новое имя
- **THEN** последующее получение возвращает новое имя

#### Scenario: Отсутствующая запись
- **WHEN** передан идентификатор удалённой, чужой или отсутствующей записи
- **THEN** сервис возвращает ошибку «не найдено» соответствующего типа

### Requirement: Логическое удаление дополнительного типа
Каждый сервис SHALL выполнять soft-delete записи текущей организации без физического удаления доменного объекта.

#### Scenario: Удаление записи
- **WHEN** вызывается delete для активной записи текущей организации
- **THEN** последующие get и list не возвращают эту запись

### Requirement: Контракты DTO
Для каждого типа SHALL существовать неизменяемые DTO `XxxView`, `CreateXxxRequest` и `XxxFilter`; представление SHALL содержать идентификатор, `number`, `name`, `createdAt` и `updatedAt`.

#### Scenario: Представление сущности
- **WHEN** активная доменная запись преобразуется в ответ сервиса
- **THEN** DTO содержит её идентификатор, номер, имя и временные метки
