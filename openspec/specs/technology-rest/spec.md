# technology-rest Specification

## Purpose
Предоставляет tenant-scoped HTTP-контракт для создания и управления технологическими процессами и их операциями по пути `/api/v1/technology-processes`.

## Requirements

### Requirement: REST создание, чтение и список процессов
REST SHALL предоставлять `POST /api/v1/technology-processes` (201), `GET /api/v1/technology-processes/{id}` (200) и `GET /api/v1/technology-processes` (200) с необязательным параметром `partId`.

#### Scenario: Создание и чтение
- **WHEN** клиент отправляет валидные `number`, `name` и `partId`
- **THEN** POST возвращает статус 201 с представлением процесса, а GET созданного процесса возвращает статус 200

#### Scenario: Список с фильтром по детали
- **WHEN** клиент запрашивает список с параметром `partId`
- **THEN** ответ содержит только процессы указанной детали текущей организации

### Requirement: REST изменение процесса
REST SHALL предоставлять `PUT /api/v1/technology-processes/{id}/name` (204) и `DELETE /api/v1/technology-processes/{id}` (204).

#### Scenario: Переименование и удаление
- **WHEN** клиент переименовывает процесс и затем удаляет его
- **THEN** операции возвращают 204, а последующее чтение процесса возвращает 404

### Requirement: REST операции процесса
REST SHALL предоставлять `POST /api/v1/technology-processes/{id}/operations` (201) и `DELETE /api/v1/technology-processes/{id}/operations/{number}` (204). Тело `POST` SHALL принимать опциональное поле `equipmentId` (`{"value": UUID}` или отсутствующее), а ответ и представление операции SHALL содержать `equipmentId` (nullable).

#### Scenario: Добавление и удаление операции
- **WHEN** клиент добавляет операцию и затем удаляет её по номеру
- **THEN** операции возвращают 201 и 204 соответственно, а последующее чтение процесса не содержит операцию

#### Scenario: Добавление операции с оборудованием
- **WHEN** клиент отправляет `POST .../operations` с телом `{number, name, equipmentId}`
- **THEN** ответ возвращает 201, а представление операции содержит переданный `equipmentId`

#### Scenario: Добавление операции без оборудования
- **WHEN** клиент отправляет `POST .../operations` с телом `{number, name}` без `equipmentId`
- **THEN** ответ возвращает 201, а представление операции содержит `equipmentId = null`

### Requirement: REST дефолтность процесса
REST SHALL предоставлять `PUT /api/v1/technology-processes/{id}/default` (204) и `DELETE /api/v1/technology-processes/{id}/default` (204).

#### Scenario: Назначение и снятие дефолтности
- **WHEN** клиент делает процесс дефолтным и затем снимает дефолтность
- **THEN** обе операции возвращают 204, а итоговое состояние соответствует запрошенному

### Requirement: REST ошибки процессов
REST SHALL возвращать 404 с кодом `not_found` для отсутствующего, удалённого или чужого процесса либо операции, 409 с кодом `duplicate` для дубликата номера процесса или номера операции, 409 с кодом `invalid_state` для нарушения инварианта дефолтности, 400 с кодом `bad_request` для ошибок валидации, 404 для отсутствующей или чужой детали при создании и 404 для отсутствующего, удалённого или чужого оборудования при добавлении операции.

#### Scenario: Отсутствующий ресурс
- **WHEN** запрос адресует чужой или удалённый процесс либо отсутствующую операцию
- **THEN** ответ имеет статус 404 и код `not_found`

#### Scenario: Дубликат номера процесса
- **WHEN** создание получает номер, уже занятый активным процессом организации
- **THEN** ответ имеет статус 409 и код `duplicate`

#### Scenario: Дубликат номера операции
- **WHEN** добавление получает номер операции, уже существующий в процессе
- **THEN** ответ имеет статус 409 и код `duplicate`

#### Scenario: Нарушение инварианта дефолтности
- **WHEN** операция снятия дефолтности нарушает инвариант дефолтного процесса
- **THEN** ответ имеет статус 409 и код `invalid_state`

#### Scenario: Ошибка валидации
- **WHEN** запрос содержит пустой `number`, пустое `name` или `null`-`partId`
- **THEN** ответ имеет статус 400 и код `bad_request`

#### Scenario: Отсутствующая деталь при создании
- **WHEN** создание получает `partId` несуществующей или чужой детали
- **THEN** ответ имеет статус 404 и код `not_found`

#### Scenario: Отсутствующее оборудование при добавлении операции
- **WHEN** добавление операции получает `equipmentId` отсутствующего, удалённого или принадлежащего другой организации оборудования
- **THEN** ответ имеет статус 404 и код `not_found`, а операция не добавляется

### Requirement: REST без пагинации и поиска
REST SHALL не поддерживать пагинацию и полнотекстовый поиск; единственный фильтр списка SHALL быть параметр `partId`.

#### Scenario: Список без пагинации
- **WHEN** клиент запрашивает список процессов без параметров пагинации
- **THEN** ответ содержит полный список активных процессов текущей организации, а фильтрация возможна только по `partId`

### Requirement: REST tenant-контекст
REST SHALL определять организацию только через серверный `OrganizationContext` и SHALL игнорировать клиентский заголовок `X-Organization-Id` и tenant в URL или теле запроса.

#### Scenario: Игнорирование клиентского tenant
- **WHEN** клиент организации A передаёт заголовок `X-Organization-Id` организации B
- **THEN** операция выполняется в контексте организации A, а данные организации B не раскрываются

### Requirement: Модуль web зависит от technology
Декларация модуля `web` SHALL включать разрешённую зависимость `technology :: technology`, а граф модулей SHALL оставаться ацикличным.

#### Scenario: Проверка зависимости web
- **WHEN** выполняется `ApplicationModules.verify()`
- **THEN** проверка проходит, зависимость `web -> technology` разрешена, циклов в графе нет
