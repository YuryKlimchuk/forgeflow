# frontend-catalog Specification

## Purpose

Предоставляет пользователю веб-интерфейс для просмотра и управления деталями каталога через существующий REST-контракт ForgeFlow.

## Requirements

### Requirement: Отображение списка деталей
Приложение SHALL отображать на одном экране таблицу активных записей выбранного типа каталога с колонками номера, названия и даты создания.

#### Scenario: Успешная загрузка списка
- **WHEN** приложение открывает экран каталога и `GET /api/v1/parts` возвращает массив деталей
- **THEN** таблица содержит для каждой детали значения `number`, `name` и `createdAt`

#### Scenario: Переключение типа
- **WHEN** пользователь выбирает вкладку «Покупные»
- **THEN** приложение загружает `/api/v1/buys` и отображает записи Buy в общей таблице

#### Scenario: Начальное состояние
- **WHEN** приложение открывает экран каталога
- **THEN** выбрана вкладка «Детали» и загружается `/api/v1/parts`

### Requirement: Создание детали
Пользователь SHALL иметь возможность создавать запись выбранного типа через общую форму, отправляя `POST` на endpoint выбранного типа.

#### Scenario: Успешное создание
- **WHEN** пользователь вводит номер и название и отправляет форму, а API возвращает 201 с созданной деталью
- **THEN** приложение отображает созданную деталь в списке и очищает форму

#### Scenario: Создание Assembly
- **WHEN** выбрана вкладка «Сборки», пользователь отправляет валидные номер и название
- **THEN** приложение отправляет `POST /api/v1/assemblies` и добавляет созданную запись в таблицу

### Requirement: Переименование детали
Пользователь SHALL иметь возможность переименовать запись выбранного типа только на детальной странице записи, отправляя `PUT /api/v1/{type}/{id}/name`.

#### Scenario: Успешное переименование
- **WHEN** пользователь подтверждает новое непустое название, а API возвращает 204
- **THEN** приложение отображает новое название у соответствующей детали

#### Scenario: Переименование на детальной странице
- **WHEN** пользователь открывает деталь, выбирает «Переименовать», вводит непустое новое название и подтверждает его, а API возвращает 204
- **THEN** детальная страница отображает новое название

#### Scenario: Переименование Vzk
- **WHEN** пользователь переименовывает запись на детальной странице вкладки «ВЗК»
- **THEN** приложение отправляет PUT на `/api/v1/vzks/{id}/name`

### Requirement: Подтверждение удаления детали
Приложение SHALL предоставлять удаление записи только на её детальной странице, SHALL запрашивать подтверждение и SHALL отправлять DELETE только после подтверждения.

#### Scenario: Удаление после подтверждения
- **WHEN** пользователь на детальной странице подтверждает удаление, а API возвращает 204
- **THEN** приложение возвращается к списку текущего типа без удалённой записи

#### Scenario: Отмена удаления
- **WHEN** пользователь отменяет подтверждение удаления на детальной странице
- **THEN** приложение не отправляет запрос DELETE и остаётся на детальной странице

#### Scenario: Отмена удаления Buy
- **WHEN** пользователь отменяет подтверждение на вкладке «Покупные»
- **THEN** запрос DELETE не отправляется

### Requirement: Отображение ошибок API
Приложение SHALL отображать человекочитаемое сообщение для ошибок API со статусами 400, 404 и 409.

#### Scenario: Дублирующий номер
- **WHEN** операция создания получает 409 с `error` равным `duplicate`
- **THEN** интерфейс сообщает, что деталь с таким номером уже существует

#### Scenario: Некорректные данные
- **WHEN** операция получает 400 с `error` равным `bad_request`
- **THEN** интерфейс отображает сообщение о некорректных данных запроса

#### Scenario: Деталь не найдена
- **WHEN** операция получает 404 с `error` равным `not_found`
- **THEN** интерфейс сообщает, что деталь не найдена

### Requirement: Состояния загрузки каталога
Приложение SHALL отображать состояние загрузки при получении списка и SHALL предотвращать повторную отправку активной операции до получения её результата.

#### Scenario: Загрузка списка
- **WHEN** `GET /api/v1/parts` находится в процессе выполнения
- **THEN** интерфейс отображает индикатор загрузки вместо завершённого результата списка

### Requirement: Визуальное оформление каталога
Интерфейс SHALL использовать светлую тему, таблицу с тонкими границами и визуальную палитру с тёмным графитовым акцентом RAL 7024 и светлой серо-бежевой подложкой RAL 7032.

#### Scenario: Отображение основного экрана
- **WHEN** пользователь открывает экран каталога
- **THEN** шапка или акцентные элементы используют цвет, соответствующий приблизительному `#474A51`, а фоновые подложки — приблизительному `#B8B4A6`

### Requirement: Вкладки типов каталога
Приложение SHALL отображать вкладки «Детали», «Сборки», «Покупные», «Стандартные» и «ВЗК», каждая из которых SHALL выбирать соответствующий endpoint и набор данных.

#### Scenario: Выбор всех вкладок
- **WHEN** пользователь последовательно выбирает пять вкладок
- **THEN** приложение использует endpoints `/api/v1/parts`, `/api/v1/assemblies`, `/api/v1/buys`, `/api/v1/standarts` и `/api/v1/vzks`

### Requirement: Generic-клиент каталога
Frontend SHALL использовать единый типизированный клиент для list, create, rename и delete операций любого из пяти типов каталога.

#### Scenario: CRUD через общий клиент
- **WHEN** пользователь выполняет создание, переименование и удаление на выбранной вкладке
- **THEN** клиент отправляет запросы с endpoint и данными текущего типа без отдельной логики запроса для каждого типа

### Requirement: Ошибки и загрузка каталога
Приложение SHALL отображать сообщения ошибок API со статусами 400, 404 и 409 и SHALL блокировать повторную активную операцию до получения её результата для выбранного типа.

#### Scenario: Пустой Buy
- **WHEN** вкладка «Покупные» открыта и API возвращает пустой массив
- **THEN** приложение показывает пустую таблицу без ошибки и позволяет создать запись

### Requirement: Управление строками спецификации
Интерфейс SHALL предоставлять на детальной странице спецификации выбранной сборки просмотр, добавление, изменения количества и удаление прямых строк спецификации.

#### Scenario: Открытие спецификации
- **WHEN** пользователь открывает «Состав» сборки
- **THEN** интерфейс отображает для каждой строки номер, название и количество после успешного GET

#### Scenario: Добавление строки
- **WHEN** пользователь выбирает тип, элемент по номеру или названию и положительное количество и подтверждает добавление
- **THEN** интерфейс отправляет POST на `/api/v1/specifications/{assemblyId}/rows` с id выбранного элемента и обновляет строки после ответа 201

#### Scenario: Изменение количества
- **WHEN** пользователь вводит новое положительное количество существующей строки
- **THEN** интерфейс отправляет PUT на `/api/v1/specifications/{assemblyId}/rows` и отображает новое количество после ответа 204

#### Scenario: Удаление строки
- **WHEN** пользователь подтверждает удаление строки спецификации
- **THEN** интерфейс отправляет DELETE на `/api/v1/specifications/{assemblyId}/rows` и исключает строку после ответа 204

### Requirement: Копирование спецификации в UI
Детальная страница спецификации SHALL предоставлять операцию «Скопировать» с вводом номера и имени новой сборки.

#### Scenario: Успешное копирование
- **WHEN** пользователь вводит валидные номер и имя и нажимает «Скопировать»
- **THEN** интерфейс отправляет `POST /api/v1/specifications/{sourceAssemblyId}/copy` и показывает созданную сборку или её идентификатор

### Requirement: Клиент спецификаций
Frontend SHALL использовать типизированные функции API для чтения, добавления, изменения, удаления и копирования строк спецификации и SHALL преобразовывать ошибки `400`, `404` и `409` в существующий формат сообщений интерфейса.

#### Scenario: Ошибка дубликата
- **WHEN** API возвращает `409` с кодом `duplicate`
- **THEN** интерфейс сообщает, что элемент уже присутствует в спецификации

#### Scenario: Ошибка валидации
- **WHEN** API возвращает `400` с кодом `bad_request`
- **THEN** интерфейс сообщает о некорректных данных

### Requirement: Состояния операций спецификации
Интерфейс SHALL отображать состояние загрузки списка спецификации и SHALL блокировать повторную отправку активной операции до получения ответа.

#### Scenario: Загрузка строк
- **WHEN** запрос строк спецификации выполняется
- **THEN** интерфейс отображает индикатор загрузки и не показывает устаревший результат как завершённый

### Requirement: Открытие детальной страницы каталога
Приложение SHALL открывать детальную страницу записи выбранного типа по клику на строку списка без изменения URL и SHALL предоставлять действие «Назад».

#### Scenario: Открытие детали Part
- **WHEN** пользователь нажимает строку записи Part в таблице
- **THEN** таблица заменяется детальной страницей этой записи с `number`, `name`, `createdAt` и `updatedAt`

#### Scenario: Возврат к списку
- **WHEN** пользователь нажимает «Назад» на детальной странице
- **THEN** приложение показывает список ранее выбранного типа без изменения URL

### Requirement: Получение данных детальной страницы
Frontend SHALL получать представление выбранной записи через `GET /api/v1/{type}/{id}` и SHALL показывать данные этой записи после успешного ответа.

#### Scenario: Успешная загрузка детали
- **WHEN** открытая детальная страница отправляет GET для записи, а API возвращает 200 с `number`, `name`, `createdAt` и `updatedAt`
- **THEN** страница отображает все четыре значения

#### Scenario: Деталь не найдена
- **WHEN** запрос детальной страницы получает 404 с кодом `not_found`
- **THEN** интерфейс показывает сообщение «Запись не найдена»

### Requirement: Создание записи на экране списка
Приложение SHALL оставлять форму создания новой записи на экране списка и SHALL НЕ показывать её как обязательную часть детальной страницы.

#### Scenario: Создание из списка
- **WHEN** пользователь находится на списке выбранного типа, заполняет номер и название и отправляет форму
- **THEN** приложение отправляет POST для текущего типа и обновляет список

### Requirement: Открытие спецификации сборки
Детальная страница Assembly SHALL предоставлять действие «Состав», открывающее детальную страницу спецификации этой сборки без ручного ввода её идентификатора.

#### Scenario: Переход к составу
- **WHEN** пользователь нажимает «Состав» на детальной странице Assembly
- **THEN** приложение показывает страницу спецификации и запрашивает `GET /api/v1/specifications/{assemblyId}/rows`

### Requirement: Ошибки и состояния операций детальных страниц
Приложение SHALL отображать человекочитаемые ошибки 400, 404 и 409 и SHALL показывать состояние загрузки для получения детали и спецификации.

#### Scenario: Ошибка конфликта
- **WHEN** переименование, удаление или операция спецификации получает 409
- **THEN** интерфейс показывает сообщение, соответствующее коду ошибки

#### Scenario: Загрузка детали
- **WHEN** GET детальной страницы выполняется
- **THEN** интерфейс показывает индикатор загрузки до получения ответа

#### Scenario: Загрузка спецификации
- **WHEN** GET строк спецификации выполняется
- **THEN** интерфейс показывает индикатор загрузки и не показывает результат как завершённый до ответа

### Requirement: Запуск плоской структуры
Детальная страница спецификации SHALL отображать кнопку «Плоская структура» и SHALL запрашивать плоский состав текущей сборки после её нажатия.

#### Scenario: Нажатие кнопки
- **WHEN** пользователь нажимает «Плоская структура»
- **THEN** frontend отправляет `GET /api/v1/specifications/{assemblyId}/flat`

### Requirement: Отображение плоского состава
Frontend SHALL отображать успешный плоский состав таблицей с колонками `number`, `name` и `quantity`.

#### Scenario: Успешный результат
- **WHEN** flat endpoint возвращает листья `Д-0001`, `Д-0002` и их количества
- **THEN** страница показывает обе строки с соответствующими номерами, названиями и количествами

### Requirement: Состояние загрузки плоской структуры
Frontend SHALL отображать состояние загрузки и SHALL блокировать повторный запуск плоской структуры до получения ответа endpoint.

#### Scenario: Выполняющийся запрос
- **WHEN** запрос плоской структуры ещё не завершён
- **THEN** кнопка недоступна и интерфейс показывает индикатор загрузки плоского состава

### Requirement: Ошибка плоской структуры
Frontend SHALL отображать человекочитаемое сообщение при ошибке плоской структуры, включая код `bom_cycle`.

#### Scenario: Обнаружен цикл
- **WHEN** flat endpoint возвращает статус `409` с кодом `bom_cycle`
- **THEN** интерфейс сообщает пользователю, что в спецификации обнаружен цикл, и не показывает частичный список

### Requirement: Поиск записей каталога
Приложение SHALL предоставлять на экране списка каталога фильтр, который оставляет записи с совпадением подстроки в `number` или `name` без учёта регистра.

#### Scenario: Совпадение по номеру
- **WHEN** список содержит запись с номером `P-100`, а пользователь вводит `p-1` в фильтр
- **THEN** таблица отображает эту запись

#### Scenario: Совпадение по названию
- **WHEN** список содержит запись с названием `Втулка`, а пользователь вводит `ТУЛ` в фильтр
- **THEN** таблица отображает эту запись

#### Scenario: Отсутствие совпадений
- **WHEN** введённый фильтр не встречается в `number` и `name` ни одной загруженной записи
- **THEN** таблица не отображает записи, не соответствующие фильтру

### Requirement: Выбор элемента для добавления строки
Форма добавления строки спецификации SHALL предоставлять селект типа и выпадающий список только элементов выбранного типа с поиском по `number` или `name`.

#### Scenario: Выбор элемента выбранного типа
- **WHEN** пользователь выбирает тип `PART` и вводит в поиск выпадающего списка часть номера или названия
- **THEN** список показывает только совпадающие элементы типа `PART`

#### Scenario: Переключение типа
- **WHEN** пользователь меняет тип с `PART` на `ASSEMBLY`
- **THEN** выпадающий список показывает элементы только типа `ASSEMBLY` и исключает элементы типа `PART`

#### Scenario: Отправка выбранного элемента
- **WHEN** пользователь выбирает элемент, отображаемый по `number` и `name`, вводит положительное количество и подтверждает добавление
- **THEN** запрос POST содержит `{item:{type,id},quantity}` выбранного элемента, а пользовательский интерфейс не требует ввода id

### Requirement: Отображение строк без UUID
Таблица строк спецификации SHALL отображать колонки «Номер», «Название» и «Количество» и SHALL НЕ отображать UUID элемента.

#### Scenario: Разрешение данных строки
- **WHEN** ответ строк содержит ссылку `{type,id}`, а загруженный каталог содержит соответствующий элемент
- **THEN** таблица показывает его `number`, `name` и `quantity`

#### Scenario: UUID отсутствует в интерфейсе
- **WHEN** пользователь просматривает таблицу строк спецификации и форму добавления
- **THEN** интерфейс не показывает значение id и не содержит поля ручного ввода идентификатора
